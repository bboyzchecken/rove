- **ตรวจกับ tree จริงบน `feat/phase-2-v1`** เมื่อ 26 ส.ค. 2569 — ตัวเลขทุกตัวใน §1 คำนวณจากค่าคงที่ในโค้ด ไม่ใช่จากสมมติฐาน

> **ประโยคเดียวของเฟสนี้:** แต้มวันนี้ถูก "ตั้งราคา" จากราคาขายภายในราคาเดียว ไม่ได้ตั้งจากต้นทุนของมัน —

## 1. ทำไมต้องปิด — เลขสามชุดที่ทำให้ต้องปิด

ค่าคงที่ที่ใช้คำนวณทั้งหมดอยู่ใน [domain/points.go](apps/api/pkg/domain/points.go) และ [domain/revenue.go](apps/api/pkg/domain/revenue.go)

อัตราปัจจุบัน: `PointsPerBahtRedeemed = 8` → **1 แต้ม = ฿0.125**

| เหตุ | แต้ม | = หนี้ (฿) | รายได้ตรงจากเหตุนั้น | เพดาน |
|---|---:|---:|---|---|
| `referral` | 150 | ฿18.75 | ฿0 | ไม่มี |
| `trip_published` (ครั้งแรก) | 500 | ฿62.50 | ฿0 | ครั้งเดียว/คน |
| `trip_cloned` | 260 | ฿32.50 | ฿0 | **ไม่มี** |
| `booking_confirmed` | 480 | ฿60.00 | ค่าคอม × 70% | ไม่มี |
| `ai_draft` (ใช้) | −300 | ฿37.50 | ต้นทุนจริง = `ai_jobs.cost_usd` | โควตา/ทริป |

### 1.1 อัตรา 8 แต้ม = ฿1 อ้างอิงตัวเอง

คอมเมนต์ในโค้ดพูดตรง ๆ ว่าอัตรานี้มาจากไหน: ร่าง 1 ครั้ง = 300 แต้ม = ฿39 → 7.69 → ปัดเป็น 8

ปัญหาคือ ฿39 เป็น **ราคาป้าย** ไม่ใช่ **ต้นทุน** ของ ROVE เมื่อคนเผาแต้ม 300 แต้ม:

| เผา 300 แต้ม ไปกับ | ROVE เสียอะไรจริง ๆ |
|---|---|
| ร่าง AI 1 ครั้ง | ค่าเรียกโมเดล 1 ครั้ง — เก็บอยู่แล้วที่ `ai_jobs.cost_usd` ([aijob.go:45](apps/api/pkg/models/aijob.go)) หลักหน่วยบาท |
| โค้ดส่วนลด ฿37.50 ใช้กับเครดิต AI | รายได้ที่สละ ฿37.50 (ไม่ใช่เงินสดออก) |
| โค้ด ฿37.50 ที่ใช้ **นอกระบบ** (แผนที่คุยไว้: Agoda / `ROVETRAVEL`) | **เงินสดออกจริง ฿37.50** ถ้า ROVE เป็นคนชดเชยให้ |

แต้มหน่วยเดียวกัน ต้นทุนต่างกันได้เป็นสิบเท่า → **อัตราแลกที่มีค่าเดียวทั้งระบบเป็นสิ่งที่ผิดตั้งแต่ตั้งสมมติฐาน** ต้องเป็น "ราคาต่อชิ้นของรางวัล" ไม่ใช่ "เรตกลาง"

และตัวเลขที่ต้องใช้แทน (`cost_usd` ต่อ job) **มีเก็บอยู่แล้ว** — ยังไม่มีใครอ่านมันเพื่อตั้งราคา

### 1.2 การจองหนึ่งครั้งจ่ายออกสองทาง และขาดทุนเมื่อยอดจองต่ำกว่า ~฿1,714

การจองที่ยืนยันแล้วจ่ายออก **สองก้อนพร้อมกัน** จากเหตุเดียวกัน ([booking.handler.go:316](apps/api/pkg/handlers/api/booking.handler.go)):

1. แต้ม `PointsPerBooking = 480` → **คงที่** ไม่ว่ายอดจองเท่าไหร่
2. ส่วนแบ่งครีเอเตอร์ 30% ของค่าคอม → **ผันตามยอด**

ให้ V = ยอดจอง, r = เรตค่าคอมของพาร์ตเนอร์ (Agoda 5%, Airalo 10%, ไม่รู้จัก 3%)

```
ROVE เก็บได้   = V × r × (1 − 0.30)
ROVE จ่ายแต้ม  = 480 × ฿0.125 = ฿60   (คงที่)
คุ้มทุนเมื่อ    V × r × 0.7 = 60
```

| พาร์ตเนอร์ | r | ยอดจองคุ้มทุน |
|---|---:|---:|
| Airalo (eSIM) | 10% | **฿857** |
| Agoda / Klook / KKday | 5% | **฿1,714** |
| Booking.com | 4% | **฿2,143** |
| พาร์ตเนอร์ที่ไม่อยู่ในตาราง | 3% | **฿2,857** |

**ตัวอย่างสองด้าน (เรต Agoda):**

| | ยอดจอง ฿48,000 (เคสในเทสต์) | ยอดจอง ฿1,500 (โฮสเทลคืนเดียว) |
|---|---:|---:|
| ค่าคอม 5% | ฿2,400 | ฿75.00 |
| − ครีเอเตอร์ 30% | −฿720 | −฿22.50 |
| − แต้ม 480 | −฿60 | −฿60.00 |
| **เหลือ ROVE** | **฿1,620** | **−฿7.50** |
| จ่ายออกรวม / ค่าคอม | 32.5% | **110%** |

**eSIM คือเคสที่แย่ที่สุด:** ราคาปกติหลักร้อยต้น ๆ ต่ำกว่าจุดคุ้มทุน ฿857 แทบทุกใบ → ทุกใบที่ขายได้ ROVE จ่ายแต้มมากกว่าที่เก็บได้

> รากของปัญหาไม่ใช่ตัวเลข 480 — คือ **การจ่ายจำนวนคงที่ทับรายได้ที่เป็นเปอร์เซ็นต์** ถ้าไม่แก้รูปสมการ ยังไงก็มีช่วงยอดจองที่ขาดทุนเสมอ

### 1.3 หนี้ที่ไม่มีวันหมดอายุ ไม่มีเพดาน และไม่มีใครรู้ยอด

- **ไม่มีวันหมดอายุ** — ไม่มีคอลัมน์หมดอายุ ไม่มีงานล้างใน [points.store.go](apps/api/pkg/store/points/points.store.go) แต้มทุกแต้มที่เคยออกยังเป็นหนี้อยู่ตลอดกาล
- **ไม่มีเพดาน** — `trip_cloned` จ่าย 260 ทุกครั้ง มีการ์ดตัวเดียวคือ `source.OwnerID != userID` ([trip.handler.go:364](apps/api/pkg/handlers/api/trip.handler.go)) แปลว่าคน ๆ เดียวกดคัดลอกทริปเดิม 50 ครั้ง = 13,000 แต้ม = ฿1,625 และบัญชีที่สองของตัวเองก็ทำได้
- **ไม่มีใครรู้ยอด** — ไม่มี query ไหนคำนวณ `Σ balance ทุกคน × RV` เลย หนี้ก้อนนี้ไม่ปรากฏบนหน้าจอไหนทั้งสิ้น

> ข้อ 1.3 คือสิ่งที่คุณพูดเองว่า *"เราไม่สามารถคิดแต้มขึ้นมาลอย ๆ ได้"* — เขียนเป็นภาษาโค้ด: โปรแกรมนี้ยัง **ไม่มีมาตรวัดสักตัว**

## 2. วิธีคิดที่ถูก — 5 สมการที่ต้องตอบก่อนตั้งอัตราใหม่

นี่คือ "วิธีคิด" ที่ขอไว้ ตั้งใจให้ทำซ้ำเองได้ ไม่ใช่ตัวเลขสำเร็จรูป — **ตัวเลขที่ยังไม่มีข้อมูลจริงมารองรับ ห้ามใส่ลงโค้ด** (นั่นคือความผิดพลาดเดิมทั้งดุ้น)

### E1 · มูลค่าแต้มตอนถูกใช้ — ต่อของรางวัล ไม่ใช่ค่ากลาง

```
RV(รางวัล) = ต้นทุนส่วนเพิ่มจริงของรางวัลนั้น (฿) ÷ แต้มที่ต้องเผา
```

"ต้นทุนส่วนเพิ่มจริง" = เงินที่ออกจากบริษัทเพิ่มขึ้นเพราะคนแลกชิ้นนี้อีกหนึ่งชิ้น
ร่าง AI = ค่าโมเดล 1 ครั้ง · โค้ดพาร์ตเนอร์ที่เขาแถมให้ = ฿0 · โค้ดที่เราชดเชยเอง = ราคาเต็ม

### E2 · Breakage — แต้มที่ออกแล้วไม่มีวันถูกใช้

```
B = 1 − (แต้มที่ถูกเผา ÷ แต้มที่ออก)   วัดเป็น cohort ตามเดือนที่ออก ไม่ใช่ทั้งระบบรวมกัน
```

Benchmark ในวงการ loyalty อยู่ราว 10–30% (สูงกว่านี้มักแปลว่ารางวัลเอื้อมไม่ถึง ไม่ใช่ว่าโปรแกรมกำไรดี)
**แต่:** วันนี้ ROVE นิยาม B ไม่ได้เลย เพราะแต้มไม่หมดอายุ — แต้มที่ยังไม่ถูกใช้ยังมีสิทธิ์ถูกใช้เสมอ
→ **ตอนคำนวณครั้งแรกให้ตั้ง B = 0** (อนุรักษ์นิยม) แล้วค่อยแก้เมื่อมีข้อมูลจริงจาก M32 + expiry จาก M33

### E3 · ต้นทุนต่อแต้มที่ออก (CPP)

```
CPP = Σ( สัดส่วนแต้มที่ไหลไปรางวัล i × RV(i) ) × (1 − B) + ค่าดำเนินการต่อแต้ม
```

จุดสำคัญ: **"สัดส่วนที่ไหลไป" คือตัวแปรที่เราคุมได้** ผ่านการตั้งราคาใน catalog
ถ้า 80% ของแต้มไหลไปรางวัลชั้น A (ต้นทุนหลักหน่วยบาท) CPP จะต่ำกว่าอัตราแลกที่ประกาศไว้มาก — **นั่นคือที่มาของกำไรของโปรแกรม ไม่ใช่ breakage**

### E4 · เพดานงบของโปรแกรม

```
(แต้มที่ออกทั้งเดือน × CPP) ≤ α × กำไรขั้นต้นของเดือนนั้น
```

Benchmark ที่ใช้ sanity-check: **α ≈ 5–10% ของกำไรขั้นต้น** หรือ **1–3% ของรายได้**
สายการบิน/โรงแรมรันสูงกว่านี้ได้เพราะต้นทุนส่วนเพิ่มของรางวัล (ที่นั่งว่าง/ห้องว่าง) เกือบศูนย์ — **ROVE เข้าข่ายนั้นเฉพาะรางวัลชั้น A เท่านั้น**

### E5 · อัตราจ่ายต่อเหตุ ต้องอนุมานจาก E4 ไม่ใช่ตั้งจากความรู้สึก

แยกเหตุออกเป็นสองประเภท แล้วใช้กฎคนละข้อ:

| ประเภท | เหตุ | กฎ |
|---|---|---|
| **มีรายได้ผูกอยู่** | `booking_confirmed` | จ่ายเป็น **% ของกำไรที่เหตุนั้นทำได้** — คูณ ไม่ใช่บวก จึงเป็นบวกเสมอโดยโครงสร้าง |
| **ไม่มีรายได้ผูกอยู่** | `referral`, `trip_published`, `trip_cloned` | เป็น **CAC** จ่ายจากงบตลาด · ต้องมีเพดานต่อคนต่อเดือน · ต้องเทียบกับ CAC ช่องทางอื่นได้ |

**รูปสมการที่เสนอสำหรับ `booking_confirmed`:**

```
แต้ม = round( V × r × (1 − ส่วนแบ่งครีเอเตอร์) × k ÷ RV_อ้างอิง )
```

โดย k = สัดส่วนกำไรที่ยอมคืนกลับเป็นแต้ม (เสนอเริ่มที่ k = 10%, ต้องเคาะใน **D6.3**)

ลองแทนค่า Agoda, k = 10%, RV อ้างอิง ฿0.125:

| ยอดจอง | ROVE เก็บได้ | คืนเป็นแต้ม (10%) | = แต้ม | เทียบของเดิม |
|---:|---:|---:|---:|---|
| ฿1,500 | ฿52.50 | ฿5.25 | 42 | 480 → **ลด 91%** |
| ฿12,000 | ฿420 | ฿42 | 336 | 480 |
| ฿48,000 | ฿1,680 | ฿168 | **1,344** | 480 → **เพิ่ม 180%** |

**อ่านตารางนี้ให้ออก:** ของใหม่ไม่ได้ "ขี้เหนียวลง" — มัน *ใจกว้างขึ้นมาก* กับการจองที่ทำเงินจริง และเลิกจ่ายกับการจองที่ทำให้ขาดทุน นี่คือสิ่งที่สมการคูณให้ แต่สมการบวกให้ไม่ได้

และในทางจิตวิทยามันยัง **อ่านง่ายกว่าเดิม** ด้วย เพราะเล่าเป็นประโยคเดียวได้ว่า *"ได้แต้มคืน 10% ของรายได้ที่แพลนคุณทำได้"* ซึ่งชัดกว่า "480 แต้มต่อการจอง" ที่ไม่มีใครรู้ว่ามาจากไหน

## 3. จิตวิทยาการตลาด — 6 กลไกที่ใช้จริง และที่ ROVE ทำผิดอยู่ตอนนี้

| # | กลไก | ใช้ยังไงกับ ROVE | วันนี้เป็นยังไง |
|---|---|---|---|
| 1 | **Perceived value ≫ marginal cost** | รางวัลที่ดีที่สุดคืออันที่ผู้ใช้ตีค่า ฿100 แต่เราจ่ายจริง ฿5 → ร่าง AI, โควตาเพิ่ม, ตัวละคร/ธีมพิเศษ, badge บนโปรไฟล์สาธารณะ | ❌ รางวัลเดียวที่มีคือส่วนลดเงินสด ซึ่งเป็นกรณีที่ *แย่ที่สุด* ในแกนนี้ (perceived = cost เป๊ะ ๆ) |
| 2 | **Goal-gradient effect** (Kivetz et al., 2006) — คนเร่งความพยายามเมื่อใกล้เป้า | รางวัลใบแรกต้องเอื้อมถึงได้ใน **~2–4 สัปดาห์** ของพฤติกรรมปกติ และต้องมีแถบความคืบหน้าให้เห็น | ❌ ระดับต่ำสุดคือ 400 แต้ม แต่ไม่มีใครรู้ว่ายอดคงเหลือมัธยฐานคือเท่าไหร่ (M32 ต้องตอบ) — ถ้าเอื้อมไม่ถึง มันไม่ใช่ "เป้าหมาย" มันคือ "ป้ายที่มองไม่เห็น" |
| 3 | **Endowed progress** (Nunes & Drèze, 2006) — แจกความคืบหน้าก้อนแรกฟรี คนจะเดินต่อ | `PointsPerPublish = 500` **เป็นกลไกนี้อยู่แล้วโดยบังเอิญ** → เปลี่ยนคำพูดจาก "ค่าตอบแทนการเปิดสาธารณะ" เป็น "ออกตัวให้ 500 แต้ม เหลืออีก X ถึงสิทธิ์แรก" | ⚠️ ของถูกแล้ว แต่เล่าผิดเรื่อง |
| 4 | **Loss aversion + วันหมดอายุ** | แต้มที่มีวันหมดอายุถูกใช้จริงมากกว่า และทำให้หนี้มีอายุ · มาตรฐานคือ **หมดอายุแบบหมุน 12–24 เดือนนับจากความเคลื่อนไหวล่าสุด + เตือนล่วงหน้า 30 วัน** | ❌ ไม่มีวันหมดอายุเลย (§1.3) |
| 5 | **ราคาอ้างอิง และข้อห้ามลดค่าเงิน** | ผู้ใช้จำอัตราแลกได้และยึดเป็นราคาอ้างอิงทันที · การ **ลดค่าแต้มภายหลังคือสิ่งที่ฆ่าโปรแกรมสะสมแต้มมากที่สุด** (ทุกเคสของสายการบิน) | ⚠️ นี่คือเหตุผลที่ **ต้องปิดตอนนี้แทนที่จะแก้เรตทีหลัง** — ปิดตอนที่ยังไม่มีใครยึดเป็นราคาอ้างอิง ราคาถูกที่สุด |
| 6 | **Scarcity + curation** (โมเดล "สิทธิพิเศษ" ของแอปธนาคารที่อ้างถึง) | จำนวนจำกัดต่อเดือน + หมุนของใหม่ทุกเดือน → คุมต้นทุนได้ **และ** ดัน perceived value ขึ้นพร้อมกัน · เป็นเหตุผลที่ต้องมี `stock` และ `per_user_limit` ใน catalog ตั้งแต่วันแรก | ❌ ไม่มีแนวคิดนี้เลย ระดับราคาคงที่ ไม่จำกัดจำนวน ไม่มีการหมุน |

**เส้นที่ห้ามข้าม:** ไม่ใช้ countdown ปลอม, ไม่ใช้ "เหลือ 2 ชิ้นสุดท้าย" ที่ไม่จริง, ไม่ทำวันหมดอายุให้หาไม่เจอ
กลไก 1–6 ได้ผลเพราะมันจริง — โปรแกรมสะสมแต้มคือสัญญาระยะยาว และสัญญาที่โกงครั้งเดียวคือสัญญาที่จบ

## 4. โครงที่เสนอ — แยก "ขาได้" ออกจาก "ขาใช้"

ความผิดพลาดเชิงโครงสร้างของของเดิมคือ **มีอัตราเดียวเชื่อมสองขาเข้าด้วยกัน** ทำให้แก้ข้างหนึ่งแล้วอีกข้างพังตาม

```
ขาได้ (earn)            ledger (มีแล้ว ถูกแล้ว)        ขาใช้ (burn)
─────────────           ────────────────────           ─────────────
อัตราจาก E5             user_points                    ราคาจาก perceived value
+ เพดานต่อคน            append-only                    + ต้นทุนจริงต่อชิ้น
+ กันโกง                ทุกแถวมีที่มา                   + stock / limit / หมุนรอบ
```

**Catalog แบ่งเป็น 3 ชั้นตามต้นทุน** — ผู้ใช้ไม่ต้องรู้ว่ามีชั้น แต่บัญชีต้องแยกออกเด็ดขาด:

| ชั้น | ตัวอย่าง | ต้นทุนส่วนเพิ่มของ ROVE | บทบาท |
|---|---|---|---|
| **A · ของเราเอง** | ร่าง AI เพิ่ม, โควตาร่างรายเดือน, ตัวละคร/ธีมพิเศษ, badge บนโปรไฟล์สาธารณะ, ปักหมุดทริปใน `/explore` | หลักหน่วยบาทถึงศูนย์ | **ตัวดูดแต้มหลัก** — ยิ่งแต้มไหลมาทางนี้มาก CPP ยิ่งต่ำ (E3) ต้องตั้งราคาให้เอื้อมง่ายที่สุด |
| **B · ส่วนลดของ ROVE เอง** | ส่วนลดเครดิต AI | รายได้ที่สละ (ไม่ใช่เงินสดออก) | ตัวกลาง ใช้เป็นสะพานความน่าเชื่อถือ |
| **C · ของพาร์ตเนอร์** | `ROVETRAVEL` ลด 5% ขั้นต่ำ ฿50,000 บน Agoda ฯลฯ | **แยกสองแบบย่อยที่ต่างกันคนละโลก** ↓ | ตัวสร้าง perceived value สูงสุด และตัวเสี่ยงสูงสุด |

**C ต้องแยกเป็น C1/C2 ตั้งแต่วันแรก:**

- **C1 — พาร์ตเนอร์ออกโค้ดให้ฟรี** (co-marketing เขาได้ traffic เราได้ของแจก) → ต้นทุน ROVE = **฿0** perceived value สูงมาก → **นี่คือของที่ควรไล่ดีลให้มากที่สุดในเฟสนี้**
- **C2 — ROVE ซื้อมา/ชดเชยให้** → ต้นทุน = **เงินสดจริง** ต้องมี stock cap และงบรายเดือน

ผู้ใช้แยก C1 กับ C2 ไม่ออก (และไม่ควรต้องแยก) แต่ **งบการเงินต้องแยกออกทันที** → นี่คือเหตุผลที่ตาราง catalog ต้องเก็บ `unit_cost_thb` แยกจาก `perceived_value_thb` ไม่ใช่คอลัมน์ราคาเดียว

## 5. Data model ที่ต้องมี

ของเดิม `discount_codes` แคบเกินไปโดยตั้งใจ (มันคือ "โค้ดส่วนลดเงินสดที่ ROVE ออกเอง") — C1/C2 ยัดลงตารางนี้ไม่ได้

### 5.1 `reward_catalog` — ของรางวัลหนึ่งชิ้น (ใหม่)

| คอลัมน์ | ทำไมต้องมี |
|---|---|
| `kind` (`internal` \| `rove_discount` \| `partner_free` \| `partner_paid`) | คือชั้น A/B/C1/C2 — ตัวแยกบัญชี |
| `points_price` | ราคาแต้ม ตั้งจาก perceived value (§3.1) |
| `unit_cost_thb` | ต้นทุนส่วนเพิ่มจริง — ตัวตั้งของ E1 · **C1 = 0** |
| `perceived_value_thb` | มูลค่าที่โชว์ผู้ใช้ · **ต่างจาก unit_cost ได้และควรต่าง** |
| `stock`, `per_user_limit`, `starts_at`, `ends_at` | กลไก 6 (scarcity + หมุนรอบ) และเพดานงบ |
| `terms_th` | "ขั้นต่ำ ฿50,000 · ลด 5% · เฉพาะที่พักในญี่ปุ่น" — ของนอกระบบมีเงื่อนไขเสมอ |
| `partner`, `external_url` | โค้ดที่ใช้นอกระบบต้องบอกว่าเอาไปใช้ที่ไหน |

### 5.2 `reward_redemptions` — ใบที่ออกให้คนหนึ่งคน (ขยายจาก `discount_codes`)

เพิ่มจากของเดิม:

| คอลัมน์ | ทำไมต้องมี |
|---|---|
| `catalog_id` | ใบนี้มาจาก SKU ไหน |
| `points_spent` | **มีอยู่แล้ว** ✅ |
| `unit_cost_thb_at_issue` | **สแนปช็อตต้นทุน ณ วันออก** — แบบเดียวกับที่ `creator_earnings.share_percent` ทำอยู่แล้ว ([revenue.go](apps/api/pkg/domain/revenue.go)) · เปลี่ยนราคาใน catalog ต้องไม่ย้อนไปแก้ต้นทุนของใบที่ออกไปแล้ว |
| `state` (`issued`→`delivered`→`used`\|`expired`\|`revoked`) | ของนอกระบบยืนยันการใช้ไม่ได้ทันที ต้องมีสถานะ "ส่งมอบแล้วแต่ยังไม่รู้ว่าใช้ยัง" |
| `external_code` | โค้ดพาร์ตเนอร์ไม่ได้อยู่ในรูป `ROVE-XXXXXX` |

### 5.3 หมดอายุของแต้ม

**ไม่เพิ่มคอลัมน์ `expires_at` ในตาราง ledger** — ledger เป็น append-only และนั่นคือสิ่งที่ทำให้มันเชื่อถือได้
ให้เขียนแถวติดลบ `reason = 'expired'` จากงานตามรอบแทน · ผู้ใช้จึงเห็นบรรทัด "แต้มหมดอายุ −250" ในประวัติ ซึ่งเป็นสิ่งที่ต้องเห็น

### 5.4 รายงานหนี้ (ไม่ใช่ตาราง — เป็น query)

```
หนี้คงค้าง = Σ(ยอดคงเหลือทุกคน) × RV เฉลี่ยถ่วงน้ำหนักตาม mix การใช้จริง
```
ต้องอยู่บนหน้าแอดมิน ไม่ใช่ในสคริปต์ที่ต้องรันเอง (M32)

## 7. ต้องวัดอะไรก่อน — และของที่มีอยู่แล้ว

**มีอยู่แล้ว ไม่ต้องสร้างใหม่:**

| ของ | อยู่ที่ไหน |
|---|---|
| ledger ของแต้มครบทุกแถว มี `reason` / `trip_id` / `occurred_at` | [models/points.go](apps/api/pkg/models/points.go) — append-only ตั้งแต่แรก |
| ต้นทุนจริงต่อการเรียก AI หนึ่งครั้ง | `ai_jobs.cost_usd` ([aijob.go:45](apps/api/pkg/models/aijob.go)) |
| แพตเทิร์นสแนปช็อตอัตรา ณ วันบันทึก | `creator_earnings.share_percent` |
| `points_spent` ต่อโค้ดที่ออก | `discount_codes` |

**ยังไม่มี — และคือทั้งหมดของ M32:**

1. แต้มที่ออก/ถูกเผา ต่อเดือน **แยกตาม reason**
2. หนี้คงค้างรวม (§5.4)
3. ยอดคงเหลือ **มัธยฐาน** และการกระจาย → ตอบกลไก 2 ว่ารางวัลใบแรกควรราคาเท่าไหร่
4. การกระจาย **มูลค่าการจอง** → ตอบว่า §1.2 เสียเงินไปแล้วเท่าไหร่จริง ๆ
5. Breakage แยก cohort (นิยามได้หลังมี expiry จาก M33)
6. ต้นทุนส่วนเพิ่มต่อรางวัลหนึ่งชิ้น

> **กฎเหล็กของเฟสนี้: ห้ามตั้งอัตราใหม่ก่อนที่ข้อ 1–4 จะมีเลขจริง** ถ้าตั้งก่อน ก็คือทำสิ่งเดิมซ้ำอีกรอบ — เดาแล้วเขียนลงโค้ด

## 8. ลำดับงานที่เสนอ (M32–M37)

### M32 — วัดอย่างเดียว ไม่แตะอัตราแม้แต่ตัวเดียว
- [ ] A32.1 `GET /admin/points/summary` — ออก/เผา/คงเหลือ รายเดือน แยกตาม reason
- [ ] A32.2 หน้าแอดมิน "หนี้แต้ม" — ยอดคงค้าง, การกระจายยอดคงเหลือ, มัธยฐาน
- [ ] A32.3 รายงานการกระจายมูลค่าการจอง + กำไรที่แท้จริงต่อการจอง (§1.2 ต่อแถว)
- [ ] A32.4 อ่าน `ai_jobs.cost_usd` ย้อนหลัง → ต้นทุนจริงต่อการร่างหนึ่งครั้ง
- [ ] A32.5 เอกสารบันทึกเลขตั้งต้นทั้งหมด ลงในเอกสารนี้ §1 (แทนที่ตัวอย่าง)

### M33 — ปิดรูที่พิสูจน์แล้วว่าเสียเงิน (ทำได้เลย ไม่ต้องรอ catalog)
- [ ] A33.1 `booking_confirmed` เปลี่ยนเป็นสมการคูณตาม E5 (ตาม **D6.3**)
- [ ] A33.2 เพดาน `trip_cloned` — ต่อคนที่คัดลอก ต่อทริป ต่อเดือน (ตาม **D6.4**)
- [ ] A33.3 แต้มหมดอายุแบบหมุน + แถวติดลบ `reason='expired'` + เตือนล่วงหน้า (ตาม **D6.5**)
- [ ] A33.4 เพดานแต้มต่อคนต่อเดือนของทุกเหตุที่ไม่มีรายได้ผูกอยู่
- [ ] A33.5 เทสต์: ทุกเหตุที่มีรายได้ผูกอยู่ต้องให้มาร์จิ้นเป็นบวกที่ทุกยอดจอง

### M34 — Reward catalog (หลังบ้านก่อน)
- [ ] A34.1 ตาราง `reward_catalog` + `reward_redemptions` + migration จาก `discount_codes`
- [ ] A34.2 แอดมิน CRUD ของรางวัล + stock + รอบเวลา + `unit_cost_thb`
- [ ] A34.3 รายงานต้นทุนต่อ SKU และ CPP ตาม E3

### M35 — หน้าสิทธิพิเศษ + คูปองของฉัน (หน้าบ้าน)
- [ ] A35.1 `/rewards` — catalog + แถบความคืบหน้าต่อชิ้น (กลไก 2)
- [ ] A35.2 `/rewards/mine` — คูปองของฉัน 3 สถานะ
- [ ] A35.3 ยกไดอะล็อกยืนยันเดิมมาใช้ต่อ ([points-redeem.tsx](apps/web/components/profile/points-redeem.tsx))
- [ ] A35.4 โปรไฟล์เหลือแค่ยอดคงเหลือ + ทางเข้า
- [ ] A35.5 `/points` เพิ่มบรรทัดหมดอายุ + คำเตือนล่วงหน้า

### M36 — พาร์ตเนอร์
- [ ] A36.1 แยก C1 (ฟรี) / C2 (จ่ายเงิน) ในบัญชีและในรายงาน
- [ ] A36.2 การส่งมอบโค้ดพาร์ตเนอร์ + สถานะ `delivered` ที่ยืนยันการใช้ไม่ได้
- [ ] A36.3 เงื่อนไขภาษาไทยต่อชิ้น + ทางออกไปเว็บพาร์ตเนอร์

- [ ] A37.1 `domain.RedemptionOpen = true` พร้อมอัตราที่คำนวณจาก E1–E5
- [ ] A37.2 หน้าอธิบายอัตราแบบสาธารณะ (กลไก 5 — ประกาศครั้งเดียว แล้วห้ามลดค่า)
