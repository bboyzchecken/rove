## 1. เราทำอะไร

ROVE คือ **แพลนเนอร์ทริปสำหรับกลุ่มเพื่อน** ที่รับข้อมูล "ที่อยากไป" ของแต่ละคน แล้วจัดออกมาเป็นตารางรายวันที่ทุกคนแก้ร่วมกันได้ พร้อมเหตุผลกำกับว่าทำไมถึงจัดแบบนั้น และมีปุ่มจองที่ต่อไปยัง agent จริงในทุกรายการ

**ปัญหาที่แก้:** ทริปกลุ่มพังตรงจุดเดียวกันทุกครั้ง — แต่ละคนมีที่อยากไปคนละที่ ไม่มีใครอยากตัดสินใจแทนเพื่อน สุดท้ายจบที่แชทยาว 300 ข้อความ กับคนหนึ่งคนที่แบกทั้งทริปไว้คนเดียว

**ทำไมของที่มีอยู่ไม่แก้ปัญหานี้**

| ทางเลือกเดิม | ขาดอะไร |
|---|---|
| AI planner (ChatGPT, Layla, Mindtrip) | คนเดียวคุยกับ AI — ไม่มี wishlist รายคน ไม่มีโหวต ไม่มีการเทียบแผน |
| แพลนใน Pantip / TikTok / บล็อก | ก๊อปมาปรับวันกับงบของตัวเองไม่ได้ และจองต่อในที่เดียวไม่ได้ |
| Agent จัดให้ (฿1,000–3,000) | แพง ช้า และแก้เองระหว่างทางไม่ได้ |
| Google Sheet + แชท | ฟรี แต่คือปัญหาที่กำลังจะแก้ |

**ปลายทาง (V2+):** เทียบราคา real-time แบบ Google Flights แต่สำหรับทริปทั้งทริป ไม่ใช่แค่ตั๋วเครื่องบิน — ระยะนี้ทำแค่พาไปหา agent แล้วรับค่าคอม

## 2. Business Model Canvas

### 2.1 กลุ่มลูกค้า (Customer Segments)

**หลัก — กลุ่มเพื่อนคนไทยวัยทำงาน 24–38 ปี ที่ไปเที่ยวญี่ปุ่นกันเป็นกลุ่ม 3–6 คน**
มีรายได้ประจำ จองเองออนไลน์เป็น ใช้ LINE เป็นช่องทางหลักในการคุยกันเรื่องทริป และมีคนหนึ่งในกลุ่มที่รับบทคนจัดทริปโดยไม่ได้อาสา — **คนคนนั้นคือผู้ใช้ที่เราออกแบบให้**

**รอง — ครีเอเตอร์และอินฟลูฯ สายเที่ยว**
มีคนถามหาแพลนอยู่แล้วแต่ไม่มีที่ให้ ตอบซ้ำ ๆ ในคอมเมนต์ · ได้ส่วนแบ่ง 30% ของค่าคอมเมื่อคนเที่ยวตามแพลนแล้วจอง · กลุ่มนี้เล็กแต่เป็นแหล่งของแพลนสาธารณะที่คนอื่นก๊อป จึงเป็นเครื่องยนต์การเติบโต ไม่ใช่แค่ลูกค้า

**ไม่ใช่ลูกค้าเรา (ระบุไว้เพื่อไม่ให้หลงทาง):** นักเดินทางคนเดียว (ไม่มีปัญหาการประสานงาน) · กรุ๊ปทัวร์ (มีคนจัดให้แล้ว) · backpacker งบต่ำ (ไม่จองออนไลน์ ค่าคอมต่ำ)

### 2.2 คุณค่าที่ส่งมอบ (Value Propositions)

| กับใคร | คุณค่า |
|---|---|
| คนจัดทริป | ไม่ต้องเป็นคนตัดสินใจแทนเพื่อนอีกต่อไป — ระบบรวบ wishlist ทุกคนแล้วจัดให้ พร้อมเหตุผลที่ยกไปอธิบายในกลุ่มได้ |
| สมาชิกในกลุ่ม | เห็นว่าที่ตัวเองอยากไปถูกใส่หรือถูกตัดเพราะอะไร โหวตได้ ไม่ต้องเกรงใจ |
| ทุกคน | ประหยัดเวลาวางแผน ~15 ชั่วโมงต่อทริป · งบและรายจ่ายจริงอยู่ที่เดียวกับแผน |

```
จองผ่าน ROVE (~30%)  → คืน ฿299 · เก็บค่าคอม ฿1,450   ลูกค้ารู้สึกว่าวางแผนฟรี

─────────────────────────────────────────────────────────
มูลค่าคาดหวัง = (0.30 × ฿1,450) + (0.70 × ฿299) = ฿644 ต่อทริปที่ซื้อ pass
```

**แก้ 15 ก.ย. 2569:** สูตรข้างบนถูกสำหรับ "ทริปเฉลี่ย" แต่จองมูลค่าต่ำ (เช่นโฮสเทลคืนเดียว) คืน
฿299 เต็มจำนวนแล้วขาดทุนได้จริง — ดู [decision-log.md](decision-log.md) 15 ก.ย. 2569 เครดิตคืนจึงไล่ขั้น
`min(฿299, ค่าคอม − ต้นทุนขาย)` แทนจำนวนคงที่ และมีกลไกใหม่ "เครดิตคืนผู้จอง" (α% ของกำไรที่เหลือ)
เพิ่มเข้ามาจากข้อเสนอผู้ทดสอบ Feedback #4 — รายละเอียดเต็มอยู่ §3.1

## 3. ต้องมีลูกค้ากี่คนถึงคุ้มทุน

> **แก้ทั้งหมด 15 ก.ย. 2569** — สูตรเดิมของ §3.1 ไม่เคยหักส่วนแบ่งครีเอเตอร์และค่าธรรมเนียม
> payment gateway ออกจากค่าคอม ทำให้กำไรต่อทริปสูงเกินจริง ไล่โค้ดจริงยังพบด้วยว่าการจองยืนยัน
> หนึ่งครั้งจ่ายออก **3 ทางพร้อมกัน** (ส่วนแบ่งครีเอเตอร์ + แต้มครีเอเตอร์ 480 + เครดิตคืน Trip
> Pass ฿299) ไม่ใช่แค่ 2 ทาง ที่มาและเหตุผลทั้งหมดอยู่ใน [decision-log.md](decision-log.md)

### 3.1 ต้นทุนเต็มต่อทริป

**ชั้นต้นทุนที่ต้องหักก่อนถึงกำไรขั้นต้น (COGS — ติดลบไม่ได้โดยโครงสร้างเพราะเป็น % เสมอ):**

| รายการ | ต่อทริป | หมายเหตุ |
|---|---:|---|
| AI ร่างแพลน | ฿2 (ฟรี) / ฿6 (Pass) | จากค่าคงที่ในโค้ดจริง |
| ค่าธรรมเนียม payment gateway | 4% ของ ฿299 ≈ ฿12 | **ยังไม่ยืนยัน** รอสมัคร gateway จริง (A20.8) |
| ส่วนแบ่งครีเอเตอร์ (s) | s% ของค่าคอมที่จองสำเร็จ **เฉพาะทริปที่คัดลอกมา** (~26% ของทริปทั้งหมด) | เดิม 30% คงที่ → **เปลี่ยนเป็นค่าที่ตั้งจากหลังบ้านได้ เริ่มที่ 15%** (เหตุผล §3.1.1) |

**ชั้นของแจกที่หักจากกำไรขั้นต้นเท่านั้น (ไล่ขั้น ไม่หักอิสระต่อกัน — กันไม่ให้ติดลบ):**

```
เหลือหลังต้นทุนขาย = ค่าคอม − AI − gateway − ส่วนแบ่งครีเอเตอร์(s%)
เครดิตคืน Trip Pass = min(฿299, เหลือหลังต้นทุนขาย)      ← ไม่ใช่ ฿299 เต็มเสมอ (แก้จากเดิม)
เหลือหลังเครดิตคืน  = เหลือหลังต้นทุนขาย − เครดิตคืน
เครดิตคืนผู้จอง (ใหม่) = α% × เหลือหลังเครดิตคืน            ← α = 5–10% (D6.2 ของ phase-6-points-economy.md)
```

สูตรนี้รับประกันว่าไม่มีทางติดลบไม่ว่ายอดจองจะเล็กแค่ไหน — เช็คกับโฮสเทล ฿1,500 (ค่าคอม Agoda
5%=฿75, s=15%): เหลือหลังต้นทุนขาย = 75−6−12−11.25 = ฿45.75 → เครดิตคืน = min(299,45.75) = **฿45.75**
(ไม่ใช่ ฿299 เต็ม) → เหลือ ฿0 → เครดิตคืนผู้จอง = ฿0 **ไม่ติดลบเลย** (สูตรเดิมติดลบ ฿264.50 ในเคสนี้)

**กำไรถัวเฉลี่ยต่อทริป ที่ s และ α ต่างกัน (α=8% ใช้เป็นค่าหลัก, กลางช่วง 5-10%):**

| s (ส่วนแบ่งครีเอเตอร์) | ทริปฟรี | ทริปซื้อ Pass | ถัวเฉลี่ย (70% ฟรี / 30% ซื้อ Pass) |
|---:|---:|---:|---:|
| 10% | ฿102.1 | ฿565.8 | **฿241** |
| **15% (ค่าตั้งต้น)** | ฿100.7 | ฿560.6 | **฿239** |
| 20% | ฿99.3 | ฿555.4 | **฿236** |
| 30% (ของเดิม ไม่ใช้แล้ว) | ฿96.6 | ฿545.0 | **฿231** |

**ข้อสังเกต:** ลด s จาก 30%→15% กระทบกำไรถัวเฉลี่ยทั้งพอร์ตแค่ ~฿8/ทริป เพราะทริปที่มาจากการ
คัดลอกมีสัดส่วนน้อย (~26%) — **s ควรเลือกจากแรงจูงใจของครีเอเตอร์ ไม่ใช่จากการปกป้องกำไรบริษัท**

ผู้ใช้หนึ่งคนสร้าง 0.8 ทริปต่อปี → ที่ s=15%: **฿191 ต่อคนต่อปี** หรือ **฿16 ต่อคนต่อเดือน**
(เดิมอ้างไว้ ฿217/฿18 — สูงเกินจริง ~13%)

#### 3.1.1 ทำไม s ต้องเป็นค่าที่แก้ได้ ไม่ใช่ค่าคงที่ในโค้ด

ตาม `phase-5-admin.md` B-3 — ย้าย `CreatorSharePercent` เข้าตาราง config ที่มี `effective_from`
เหมือนที่ `creator_earnings.share_percent` สแนปช็อตค่า ณ วันเกิดรายการอยู่แล้ว เปลี่ยน s ทีหลังจึง
ไม่กระทบยอดที่จ่ายไปแล้วสักบาท เริ่มที่ 15% แล้วปรับตามพฤติกรรมจริงของครีเอเตอร์โดยไม่ต้องคิดสูตร
คุ้มทุนใหม่ทุกครั้ง (ตารางข้างบนแสดงแล้วว่ากำไรบริษัทแทบไม่ขยับตาม s)

### 3.2 จุดคุ้มทุน — 3 ระดับ

ทีมยอมรับความเสี่ยงต่างระดับกันในแต่ละช่วงเวลา จึงมี 3 เกณฑ์ ไม่ใช่เกณฑ์เดียว:

| ระดับ | เงื่อนไข | ทริป/เดือน (ที่ s=15%, α=8%) | ผู้ใช้สะสมโดยประมาณ |
|---|---|---:|---:|
| **พอรับได้ระหว่างพิสูจน์ตัว** | ขาดทุนเงินสด ≤ ฿10,000/เดือน (ไม่นับค่าแรงตัวเอง — ไม่ใช่เงินสดที่ต้องหา) | **95** | ~1,410 |


> ## เป้าคุ้มทุนเต็มคือ **~4,190 ผู้ใช้** (เดิมอ้างไว้ 3,700 คน — ต่ำไปเพราะกำไรต่อทริปสูงเกินจริง)
> แต่ระหว่างทางยังมี "พอรับได้" ที่ ~1,410 คนเป็นจุดที่พิสูจน์ว่าคนใช้จริงก่อนจะดัง
> **CAC ต้องต่ำกว่า ฿86 ต่อคน** (งบตลาด ฿360,000 ต่อปี ÷ 4,190 คน) ถ้าคุมได้ ปีแรกกำไรแน่นอน

### 3.3 ทำไม 10,000 คนถึงไม่ใช่ตัวเลขที่ควรยึด

ROVE ได้เงินจากผู้ใช้แค่ **฿217 ต่อคนต่อปี** ซึ่งต่ำมากเมื่อเทียบกับสินค้า subscription ทั่วไป (Netflix ฿419/เดือน = ฿5,000/ปี) ธุรกิจ ARPU ต่ำแบบนี้มีทางรอดสองทาง: **คนเยอะระดับหลักแสน** หรือ **ทำให้แต่ละคนมีค่ามากขึ้น** — 10,000 คนอยู่ตรงกลางที่ไม่ได้ทั้งสองอย่าง จึงควรมองเป็นเป้าหมายการเติบโต ไม่ใช่เงื่อนไขการอยู่รอด

### เคสแย่ที่สุดหมายความว่าอะไรจริง ๆ

ตัวเลข −฿657,000 **ไม่ใช่เงินสดที่ต้องหามาจ่าย** เพราะ ฿420,000 ในนั้นคือค่าแรงตัวเอง

```
เงินสดที่เสียจริงในเคสแย่ที่สุด = การตลาด ฿360,000 + infra ฿31,200 = ฿391,200
```

**นี่คือตัวเลขเดียวที่ต้องตอบให้ได้ก่อนเริ่ม: รับความเสี่ยง ฿391,200 ในหนึ่งปีได้ไหม** ถ้าได้ ก็เริ่มได้ เพราะเคสฐานและเคสดีทั้งคู่กำไร และเคสแย่ยังไม่ถึงขั้นล้มละลาย

**สัญญาณเตือนที่ต้องเฝ้าตั้งแต่เดือนแรก:** ถ้า CAC เกิน ฿96 ติดกันสองเดือน แปลว่ากำลังเดินเข้าเคสแย่ — ให้หยุดซื้อสื่อแล้วกลับไปแก้ viral loop ก่อน อย่าเพิ่มงบ

## 6. ตัวคูณที่ใหญ่ที่สุด — ขยายปลายทางนอกญี่ปุ่น

คนไทยไปเวียดนาม เกาหลี ไต้หวัน บ่อยกว่าญี่ปุ่นมาก ถ้าทริปต่อคนต่อปีขยับจาก **0.8 → 1.2** รายรับส่วนเพิ่มโตขึ้น **50%** โดยไม่ต้องหาผู้ใช้เพิ่มสักคน

และงานนี้ถูกกว่าที่คิด — Decision Log 19 ส.ค. บันทึกไว้ว่า *"UI/copy พูดถึงทั่วโลก ไม่ผูกกับญี่ปุ่น"* หน้าจอถูกสร้างมารองรับทั่วโลกตั้งแต่แรกแล้ว **การขยายปลายทางจึงเป็นปัญหาข้อมูล POI ไม่ใช่การรื้อระบบ**

เทียบกับตัวคูณอื่น (ผลต่อกำไรปีแรก ฐานเดียวกัน):

| ทำอะไร | ผล | ความยาก |
|---|---|---|
| ขยายปลายทาง (0.8 → 1.2 ทริป/คน/ปี) | **+50%** | ต้องมีข้อมูล POI ประเทศใหม่ |
| เพิ่มคนซื้อ Pass (30% → 45%) | +29% | ปรับ onboarding/UX |
| เพิ่มคนจองผ่านเรา (30% → 40%) | +13% | ปรับ flow การจอง |
| ขึ้นราคา (฿299 → ฿349) | +4% | เสี่ยงคนซื้อน้อยลงจนติดลบ |

**ขึ้นราคาช่วยน้อยที่สุด** เพราะ 30% ที่จองผ่านเราได้เงินคืนอยู่แล้ว การขึ้นราคาจึงกระทบแค่ 70% ที่เหลือ และมีโอกาสทำให้คนซื้อ Pass น้อยลงจนขาดทุนสุทธิ
