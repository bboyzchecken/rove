## 2. กอง A — สิ่งที่ "แอดมินต้องจัดการได้อยู่แล้ว"

คือข้อ 1 ของโจทย์: จัดการผู้ใช้ / ชาวโรฟ · ระงับ · แบน · ให้สิทธิ์ AI
แยกตามว่า **ต้องแตะอะไรถึงจะได้มา**

### A-1 · ต่อสายอย่างเดียว (backend เสร็จแล้ว 100%)

| งาน | endpoint ที่มีอยู่ | ต้องทำ |
|---|---|---|
| แก้/เพิ่ม POI | `POST/PATCH /admin/poi` | ฟอร์ม + ตารางที่แก้ได้ |
| จัดการตัวละคร | `GET/POST /admin/characters` | หน้ารายการ + ฟอร์ม |
| คิว lead ของเอเจนต์ | `GET /admin/leads`, `PATCH /admin/leads/:id` | ตาราง + เปลี่ยนสถานะ (`new→sent→contacted→won/lost`) + ช่อง `admin_note` |
| รายงานจ่ายครีเอเตอร์ | `GET/POST /admin/payouts` | รายงานรายเดือน + ปุ่มปิดยอดทีละคน (ขั้นต่ำ ฿300 ตาม `domain.MinimumPayoutTHB`) |

**นี่คือกองที่คุ้มที่สุดต่อวันทำงาน** — ไม่มี migration ไม่มี endpoint ใหม่ ไม่มีการตัดสินใจทางธุรกิจ

### A-2 · เขียน endpoint ใหม่ แต่ data model รองรับอยู่แล้ว

| งาน | ของที่มีรองรับอยู่ | ที่ขาด |
|---|---|---|
| ลิสต์/ค้นหาผู้ใช้ | ตาราง `users` ครบ | `UserStore.List(filter, cursor)` + `GET /admin/users` |
| หน้าโปรไฟล์ผู้ใช้รายคน (มุมแอดมิน) | ทริป, `user_points`, `orders`, `creator_earnings`, `ai_jobs` มีครบทุกตาราง | endpoint รวมร่างเดียว `GET /admin/users/:id` |
| ปรับแต้มมือ | `PointsReasonAdjustment` **นิยามไว้แล้วแต่ไม่มีใครเรียก** ([points.go:17](apps/api/pkg/models/points.go)) | `POST /admin/users/:id/points` + บังคับให้กรอกเหตุผล |
| เปลี่ยน role | `users.role` | `PATCH /admin/users/:id/role` + กันแอดมินคนสุดท้ายลดสิทธิ์ตัวเอง (`CountAdmins` มีอยู่แล้ว) |
| ดู/retry AI job ที่ค้าง | `ai_jobs` มี `status='failed'` + `error` | `GET /admin/ai/jobs` + ปุ่ม retry |

### A-3 · ต้องแก้ schema หรือบังคับกฎเพิ่ม

| งาน | ทำไมยังไม่ได้ | ที่ต้องทำ |
|---|---|---|
| **ระงับ / แบน** | `status` ไม่ถูกบังคับที่ไหนเลย (§1.1) | (1) เพิ่มค่า `suspended` / `banned` + คอลัมน์ `suspended_until`, `status_reason`, `status_by` (2) **บังคับใน `JwtMiddleware`** ไม่ใช่แค่ตอน login (3) ทริป/แพลนสาธารณะ/แต้ม/ยอดค้างจ่าย → **เคาะแล้วใน [§6.3](#63-d52--ระงับ-vs-แบน-เคาะแล้ว-27-ส-ค-2569)** |
| **ให้สิทธิ์ AI** | ~~`ai_credits` เป็น per-trip ไม่มีที่เก็บสิทธิ์ระดับคน~~ **บรรทัดนี้ตกยุคตั้งแต่ Trip Pass ขึ้น** — วันนี้มีทางปลดล็อกสองทางแล้วทั้งระดับทริปและระดับคน (`unlockState`, [ai.handler.go:68](apps/api/pkg/handlers/api/ai.handler.go)) | **ไม่ต้องแก้ schema เลย** — ออกของแถมผ่านทางเดิม → [§6.2](#62-d51--ให้สิทธิ์-ai--ออกของแถมผ่านทางที่มีอยู่-เคาะแล้ว-27-ส-ค-2569) |
| **audit log ของแอดมิน** | `activity_logs` ผูก `trip_id` เสมอ ([collab.go:50](apps/api/pkg/models/collab.go)) — บันทึกการกระทำนอกทริปไม่ได้ | ตาราง `admin_audit_logs` (actor, action, target_type, target_id, before/after JSON, ip, at) — **ต้องขึ้นพร้อมปุ่มแบนปุ่มแรก ไม่ใช่ตามหลัง** |

## 3. กอง B — สิ่งที่ธุรกิจต้องมี แต่ยังไม่เคยวางแผนไว้

คือข้อ 2 ของโจทย์ ทั้งหมดนี้ **ไม่มีตาราง ไม่มี endpoint ไม่มีหน้าจอ** เว้นแต่ระบุไว้เป็นอย่างอื่น

### B-1 · ข่าว / บทความ (CMS) — เริ่มจากศูนย์

ไม่มี model ชื่อไหนใกล้เคียงเลยใน `pkg/models/` และไม่มี route `/blog` หรือ `/news` ใน `apps/web/app`

**D5.3 เคาะแล้ว → [§6.4](#64-d53--ข่าวบทความอยู่ในตาราง-เคาะแล้ว-27-ส-ค-2569): ตาราง `articles`** · ที่เขียนไว้เดิมว่า "ต้องทำ SEO เอง" เป็นการเทียบที่ไม่ยุติธรรมกับตัวเลือกนั้น — MDX ก็ไม่ได้แถม SEO มาให้เหมือนกัน (วันนี้ทั้งแอปไม่มี `sitemap.ts` และมี `generateMetadata` อยู่ไฟล์เดียว)

ถ้าเลือกตาราง ขั้นต่ำที่ธุรกิจต้องมี: หมวดหมู่, ปก, สถานะ (draft/scheduled/published), เวลาเผยแพร่, ผู้เขียน, slug, SEO title/description, และ **ผูกกับ POI/ปลายทางได้** — เพราะเหตุผลเดียวที่บทความควรอยู่บนนี้แทนที่จะเป็น Medium คือมันต้องลิงก์กลับเข้า explore ได้

### B-2 · คูปอง / แคมเปญ — **ไม่ใช่การขยายตารางเดิม**

มีตาราง `discount_codes` อยู่แล้ว แต่มันคือ "แต้มแลกโค้ด" ของผู้ใช้ (A12.10) ไม่ใช่คูปองการตลาด:

| `discount_codes` วันนี้ | คูปองการตลาดต้องการ |
|---|---|
| `user_id` **not null** — โค้ดเป็นของคนเดียว | โค้ดเดียวคนใช้ได้หลายคน |
| `points_spent` not null — โค้ดที่มีอยู่คือโค้ดที่จ่ายแต้มแล้ว | ไม่มีแต้มมาเกี่ยวเลย |
| จำนวนเงินตายตัว ฿50/฿100/฿300 (`RedemptionTiers`) | ลด % ก็ได้, มีเพดาน, มียอดขั้นต่ำ |
| ใช้ครั้งเดียว | โควตารวม + โควตาต่อคน |
| อายุ 180 วันตายตัว | มีวันเริ่ม–วันจบ |
| ไม่มีสถานะ | เปิด/ปิด/หยุดชั่วคราว |

→ **เสนอ:** ตาราง `campaigns` + `campaign_redemptions` แยกใหม่ แล้วให้จุดคิดเงินรับได้ทั้งสองชนิด · **อย่าขยาย `discount_codes`** — ตารางนั้นถือหนี้สินที่ผู้ใช้จ่ายแต้มซื้อไปแล้ว การเติมคอลัมน์ nullable ห้าตัวเข้าไปทำให้ "โค้ดใบนี้ใครจ่ายค่าอะไร" ตอบไม่ได้อีกต่อไป

ก่อนทำต้องตอบ **D5.4**: วันนี้ ROVE เก็บเงินอย่างเดียวคือ **เครดิต AI** (`DiscountScopeAICredits`) — คูปองจะเอาไปลดอะไร ถ้ายังไม่มีของอื่นให้ขาย

### B-3 · ค่าคอมมิชชั่น — ของมีครบ แต่แก้ได้ด้วยการ deploy เท่านั้น

| ตัวเลข | อยู่ที่ไหน | แก้ยังไงวันนี้ |
|---|---|---|
| เรตค่าคอมต่อพาร์ตเนอร์ (agoda 5%, booking 4%, …) | `partnerCommissionRate` map ใน [revenue.go:87](apps/api/pkg/domain/revenue.go) | แก้โค้ด + deploy |
| ส่วนแบ่งครีเอเตอร์ 30% | `CreatorSharePercent` | แก้โค้ด + deploy |
| ขั้นต่ำจ่าย ฿300 | `MinimumPayoutTHB` | แก้โค้ด + deploy |
| อัตราแลกแต้ม 8 แต้ม = ฿1 | `PointsPerBahtRedeemed` | แก้โค้ด + deploy |
| รายชื่อพาร์ตเนอร์ + catalogue ของข้อเสนอ | slice ใน [affiliate.go](apps/api/pkg/services/affiliate/affiliate.go) | แก้โค้ด + deploy |

**ที่ขาดจริง ๆ ไม่ใช่ "หน้าจอแก้ตัวเลข" แต่คือ "ตัวตนของพาร์ตเนอร์ในระบบ"** — วันนี้พาร์ตเนอร์เป็นแค่ string ในคอลัมน์ `creator_earnings.partner` ไม่มีตารางที่บอกว่ารายนี้เปิด/ปิดอยู่, เรตเท่าไหร่, ตั้งแต่เมื่อไหร่, ติดต่อใคร, postback เข้ามาล่าสุดเมื่อไหร่

ข้อที่ต้องเขียนลง spec ให้ชัด: **เรตต้องมีผลไปข้างหน้าเท่านั้น** เปลี่ยนเรตแล้ว `creator_earnings` แถวเก่าต้องไม่ขยับ ไม่งั้นยอดที่จ่ายไปแล้วกับรายงานจะไม่ตรงกัน → โชคดีที่ `share_percent` ถูกเก็บลงแถวตอนสร้างอยู่แล้ว ([partner.go:74](apps/api/pkg/models/partner.go)) ตาราง config ใหม่แค่ต้องมี `effective_from`

### B-4 · โมเดอเรชัน — ช่องว่างที่ใหญ่ที่สุดและถูกมองข้ามที่สุด

`grep -i "report|abuse|moderat"` ทั้ง `apps/api/pkg` = **ไม่เจออะไรเลย**

ของที่ผู้ใช้เผยแพร่สู่สาธารณะได้วันนี้: แพลนสาธารณะ (`trips.visibility='public'`), รีวิว (`trip_reviews`), รูป (`trip_photos`), คอมเมนต์ (`comments`), โปรไฟล์ `/u/[handle]` (ชื่อ, handle, รูป)

ธุรกิจต้องมีอย่างน้อย: ปุ่มรายงานฝั่งผู้ใช้ → คิวรายงานฝั่งแอดมิน → ซ่อน/ลบเนื้อหา → บันทึกลง audit log → แจ้งเจ้าของ

ถ้ามีข่าว บทความ และคูปอง แต่ลบรีวิวหยาบคายออกจากหน้าสาธารณะไม่ได้ นั่นคือลำดับความสำคัญที่กลับหัว

### B-5 · เงิน ใบเสร็จ และการคืนเงิน

`orders` / `subscriptions` มีครบ ([billing.go](apps/api/pkg/models/billing.go)) แต่ **แอดมินไม่มีทางเห็นแม้แต่ใบเดียว** — `registerBillingRoutes` แขวนอยู่ใต้ `users/me` เท่านั้น

- `Order.Status` มีค่า refunded และมี `RefundedAt` เตรียมไว้ แต่ **ไม่มี code path ไหนเซ็ตมัน**
- คอมเมนต์ในโมเดลบอกชัดว่า order เขียนแล้วห้ามแก้: การคืนเงินคือการเปลี่ยนสถานะ และการแก้คือออกใบใหม่ — spec ของหน้าคืนเงินต้องเคารพข้อนี้
- `Order.Simulated` แปลว่ายังไม่มี gateway จริง → หน้าคืนเงินวันนี้คือ "ทำเครื่องหมายว่าคืนแล้ว" ไม่ใช่ "โอนเงินคืน" และต้องเขียนบนจอให้ตรงตามนั้น

### B-6 · จ่ายเงินครีเอเตอร์จริง

`payouts` บันทึก "ใคร งวดไหน เท่าไหร่ สถานะอะไร" แต่ **ไม่มีที่เก็บว่าจะโอนเข้าบัญชีไหน** — ไม่มีชื่อธนาคาร ไม่มีเลขบัญชี ไม่มีข้อมูลภาษี ไม่มี KYC

→ วันนี้ปิดยอดในระบบได้ แต่การโอนจริงต้องไปถามกันนอกระบบ · ถ้าจะมีครีเอเตอร์จริง อันนี้ต้องมาพร้อม **D5.6** (เก็บข้อมูลอ่อนไหวแค่ไหน ใครเห็นได้บ้าง เก็บนานแค่ไหน)

## 4. Layout และธีมของแอดมิน

### 4.1 กฎที่ห้ามแหก

[styles/brand.css](apps/web/styles/brand.css) เขียนไว้ว่าเป็น **ที่เดียว** ที่มีสีของแบรนด์ และบรรทัดสุดท้ายของไฟล์บอกว่า dark theme คือ "การออกแบบใหม่ ไม่ใช่การสลับ token"

→ ธีมแอดมินจึงต้องเป็น **scope ที่เพิ่มในไฟล์เดิม** ไม่ใช่ไฟล์สีที่สอง:

```css
/* ต่อท้าย :root ใน brand.css */
[data-surface='admin'] { --brand-bg: 17 26% 11%; --brand-surface: 17 20% 16%; ... }
```

แล้วใส่ `data-surface="admin"` เฉพาะใต้ layout ของแอดมิน — Tailwind mapping ใน `globals.css` **ไม่ต้องแก้แม้แต่บรรทัดเดียว** เพราะทุก utility อ่าน `hsl(var(--brand-*))` อยู่แล้ว

### 4.2 สีที่เสนอ (สีเดิม เข้มขึ้น ไม่ใช่ชุดใหม่)

| token | ฝั่งผู้ใช้ | ฝั่งแอดมิน (เสนอ) | เหตุผล |
|---|---|---|---|
| `--brand-bg` | ขาว | espresso เข้ม `17 26% 11%` | espresso คือสีตัวอักษรของแบรนด์อยู่แล้ว → กลับด้านมาเป็นพื้น ได้ธีมเข้มที่ยังเป็นสีเดียวกับแบรนด์ ไม่ใช่เทากลาง ๆ ของ dashboard ทั่วไป |
| `--brand-surface` | `30 10% 96%` | `17 20% 16%` | การ์ดลอยจากพื้นด้วยความสว่าง ไม่ใช่ด้วยเงา (คงหลักการ flat เดิม) |
| `--brand-espresso` (ตัวอักษร) | `17 26% 19%` | ครีม `30 20% 92%` | |
| `--brand-muted` | `22 18% 43%` | `24 12% 62%` | ต้องผ่าน 4.5:1 บนพื้นใหม่ |
| `--brand-primary` | terracotta `15 65% 58%` | **คงเดิม** | ปุ่มหลักและ active state เท่านั้น — บนพื้นเข้มมันเด่นกว่าเดิมด้วยซ้ำ |
| accent 4 สี | บล็อกสีสนุก ๆ | ลดความอิ่ม ใช้เป็น **สถานะ** เท่านั้น: matcha = สำเร็จ · sun = รอ/เตือน · joyfull = ข้อมูล · danger = อันตราย | **นี่คือจุดที่ "เลิกการ์ตูน" เกิดขึ้นจริง** — ไม่ใช่ที่การเปลี่ยนสี แต่ที่การเลิกใช้สีเพื่อความสนุก |
| `--brand-radius` | 24px | 10px (`-sm` 6px) | ตารางข้อมูลที่มุมโค้ง 24px อ่านยาก |
| เงา | แทบไม่ใช้ | คงหลักเดิม แต่บนพื้นเข้มต้องเป็น `rgba(0,0,0,…)` ไม่ใช่สี espresso | |
| ฟอนต์ | Inter + Noto Sans Thai | **คงเดิม** และให้ `.nums` (tabular) เป็นค่าเริ่มต้นในตารางทุกใบ | |

### 4.3 โครงหน้าจอ

- **sidebar ซ้ายถาวร** (ยุบได้) + topbar บาง ๆ (ค้นหาข้ามระบบ, ป้ายบอก env/stub, บัญชีแอดมิน) + content เต็มความกว้าง
- **desktop-first** — เป็น **ข้อยกเว้นที่ตั้งใจ** ของ `DEV_SPEC` §7 ที่กำหนด mobile-first ทั้งโปรเจกต์ ต้องเขียนเหตุผลลง spec: งานแอดมินคือตารางกับฟอร์ม ไม่ใช่การยืนดูบนรถไฟ · มือถือรองรับแค่ "อ่านตัวเลข + ตอบ lead"
- **primitives ใหม่อยู่ใน `components/admin/ui/`** ห้ามยัดเข้า `components/ui/` ซึ่งเป็นของฝั่งผู้ใช้: `DataTable` (sort / paginate / เลือกหลายแถว), `FilterBar`, `Drawer` รายละเอียด, `ConfirmDangerDialog` (พิมพ์ยืนยันสำหรับแบน/ลบ), `StatusPill`, `KeyValueList`, `AuditTrail`, `MoneyCell`
- ทุกหน้าที่ทำอะไรถาวรได้ ต้องมีสามอย่างเสมอ: **ช่องเหตุผลที่บังคับกรอก · แถบ audit ของ target นั้น · ทางถอย** (ถ้าถอยไม่ได้ ต้องบอกก่อนกด ไม่ใช่หลังกด)

### 4.4 Routing — มีกับดักหนึ่งอัน

วันนี้ `app/(app)/admin/page.tsx` → `/admin` (อยู่ใน `AppShell` ของผู้ใช้) และ `app/admin/login/page.tsx` → `/admin/login`

**ถ้าสร้าง `app/admin/page.tsx` โดยไม่ลบของเดิมก่อน = build error** (สอง route group ให้ path เดียวกัน)

เสนอ: ย้ายทั้งก้อนไป `app/(admin)/admin/**` พร้อม `layout.tsx` ของตัวเอง แล้ว **ลบ `app/(app)/admin` ทิ้ง** · `app/admin/login` อยู่ที่เดิม (คนละ layout กับ dashboard — หน้า login ไม่ควรมี sidebar)

[proxy.ts](apps/web/proxy.ts) ไม่ต้องแก้เลย: `/admin` อยู่ใน `GUARDED` และ `/admin/login` อยู่ใน `OPEN` แล้ว — ตราบใดที่ URL ไม่เปลี่ยน

### 4.5 สองข้อที่คนมักลืมแล้วบานปลาย

1. **mock/live ต้องเดินได้ทั้งคู่** — repo pattern บังคับให้ทุกหน้าจอใหม่มีทั้ง [live/repo.ts](apps/web/lib/data/live/repo.ts) และ [mock/repo.ts](apps/web/lib/data/mock/repo.ts) · นี่คือ **ประมาณครึ่งหนึ่งของงานฝั่ง UI** ไม่ใช่ของแถม
2. **ภาษา** — [docs/i18n-plan.md](docs/i18n-plan.md) เขียนไว้ตั้งแต่บรรทัดแรกว่าขอบเขต i18n **ไม่รวมหน้า admin** → Phase 5 เป็นไทยล้วนโดยตั้งใจ และต้องเขียนไว้ในหัว spec ไม่งั้นรอบหน้าจะมีคนมาไล่ถอดคีย์

### 6.1 D5.7 — สิทธิ์แอดมินแบบเลือกได้รายคน (เคาะแล้ว 27 ส.ค. 2569)

**คำตอบ:** ไม่มี "ระดับ" ของแอดมิน มีแต่ **ชุดสิทธิ์ที่ติ๊กเลือกได้ทีละข้อต่อคน**
เพิ่มคนดูแลข่าวคนหนึ่ง = สร้างบัญชี → ให้สิทธิ์ `articles.write` + `articles.publish` → จบ
เขาเปิด `/admin` ได้ เห็นเมนูข่าวเมนูเดียว และยิง `PATCH /admin/users/:id` ไม่ผ่านแม้จะรู้ URL

**ทำไมไม่ทำเป็นระดับ (`support` < `editor` < `admin`):** ระดับบังคับให้ตอบคำถามที่ยังไม่มีคำตอบ —
คนดูแลข่าวควรอยู่สูงหรือต่ำกว่าคนตอบ lead? ไม่มีคำตอบ เพราะสองงานนี้ไม่ได้อยู่บนแกนเดียวกัน
พอไม่มีแกน ลำดับก็ถูกเดา แล้วรอบหน้าจะมีคนต้องการ "finance ที่ดูออเดอร์ได้แต่คืนเงินไม่ได้"
ซึ่งแทรกกลางลำดับไม่ได้

#### กติกาห้าข้อ

**1. `users.role` ไม่เปลี่ยนรูป** ยังเป็น `user` / `admin` เท่าเดิม ([user.go:14](apps/api/pkg/models/user.go))
`IsAdmin` ([middleware.go:100](apps/api/pkg/handlers/api/middleware.go)) ยังคาอยู่ที่ group `/admin` เป็นประตูบานแรก
สิทธิ์เป็น **ชั้นที่สอง** บนประตูนั้น ไม่ใช่ของที่มาแทน — แปลว่า `CountAdmins`, การ bootstrap แอดมินคนแรก
([auth.handler.go:337](apps/api/pkg/handlers/api/auth.handler.go)) และเทสต์เดิมไม่ต้องแก้สักบรรทัด

**2. สิทธิ์ห้ามอยู่ใน JWT** `Claims` มี `role` และ TTL 7 วัน ([middleware.go:17,23](apps/api/pkg/handlers/api/middleware.go))
ถ้าเอาสิทธิ์ยัดเข้าไป การถอนสิทธิ์จะมีผลจริงอีก 7 วันข้างหน้า — **บั๊กตัวเดียวกับ A26.5 เป๊ะ ๆ**
(แบนแล้ว token เดิมยังใช้ได้) แค่คนละที่เกิด → อ่านจาก DB ทุกรีเควสต์ ไม่แคช
ทราฟฟิกฝั่งแอดมินคือคนไม่กี่คนคลิกไม่กี่ครั้ง หนึ่ง query ต่อรีเควสต์คือราคาที่ถูกที่สุดที่จ่ายได้

**3. ตารางเดียว ไม่ใช่สอง**

```sql
admin_grants (user_id, permission, granted_by, granted_at)  -- unique(user_id, permission)
```

ไม่มีตาราง `roles` ให้ผูก เพราะ ROVE มีแอดมินหลักหน่วย ตารางบทบาทคือชั้น indirection
ที่ยังไม่มีใครจ่ายค่ามัน · **"ตำแหน่ง" มีอยู่จริงแค่ฝั่ง UI** — เป็นปุ่ม preset ที่ติ๊ก checkbox
ให้ทีเดียว (คนดูแลข่าว / คนตอบ lead / คนดูเงิน) แล้วแก้ทีละข้อต่อได้
วันที่แอดมินเกินสิบคนแล้วอยากได้บทบาทจริง ให้เพิ่มตารางแล้ว resolve เป็น key ชุดเดิม —
**จุดตรวจไม่ต้องแก้เลย เพราะมันถาม key ไม่เคยถามตำแหน่ง**

**4. ตรวจที่ route ทีละเส้น + default-deny ที่มีเทสต์คุม**

```go
g.POST("/poi", s.Requires("catalog.write"), s.handleAdminUpsertPOI)
```

และ **เทสต์ที่เดินตาราง route ของ echo ทั้งใต้ `/admin` แล้วแดงถ้าเส้นไหนไม่ได้ประกาศสิทธิ์**
ข้อนี้คือหัวใจ ไม่ใช่ของแถม: M28–M31 จะเพิ่ม endpoint อีกหลายสิบเส้น และวันที่มีคนลืมใส่
`Requires` จะเป็นวันธรรมดา ๆ วันหนึ่ง ไม่ใช่วันที่ใครนั่งทบทวนความปลอดภัย

**5. `admins.manage` คือ superadmin ตัวจริง — เขียนไว้ให้ตรง** คนที่ถือสิทธิ์นี้ให้สิทธิ์ตัวเองได้ทุกอย่าง
มันจึงไม่ใช่สิทธิ์ระดับเดียวกับข้ออื่น อย่าวางมันไว้ในลิสต์เฉย ๆ เหมือนเพื่อนบ้าน ·
กันตัวเอง: ถอน `admins.manage` ของตัวเองไม่ได้ถ้าเป็นคนสุดท้ายที่ถืออยู่ (ตรรกะเดียวกับ X26.2)

### 6.2 D5.1 — "ให้สิทธิ์ AI" = ออกของแถมผ่านทางที่มีอยู่ (เคาะแล้ว 27 ส.ค. 2569)

**ก่อนอื่น: ทางเลือกทั้งสองข้อในตารางข้างบนตกยุคไปแล้ว** ตอนเขียน §2 A-3 ยังไม่มี Trip Pass
วันนี้ [ai.handler.go:68](apps/api/pkg/handlers/api/ai.handler.go) `unlockState` มีทางปลดล็อกอยู่แล้วสองทาง
และมันครอบทั้งสองระดับที่ D5.1 ถามหาพอดี:

| ทาง | ปลดล็อกใคร | เก็บที่ไหน |
|---|---|---|
| Trip Pass ฿299 | **ทริปนั้นทั้งห้อง** ใครในห้องจ่ายก็ได้ | `orders` (kind `trip_pass`) |
| Rove Year ฿990 | **ทุกทริปของคนนั้น** ตลอดปี | `subscriptions` (plan `rove_year`) |

**คำตอบ: ไม่สร้างอะไรใหม่เลย — "ให้สิทธิ์ AI" คือการออกของสองอย่างนี้ในราคา ฿0 พร้อมเหตุผล**

- `POST /admin/trips/:id/pass` → order kind `trip_pass`, `total_thb = 0`, `method = 'comp'` — ห้องนั้นปลดล็อก
  ใช้กับเคสซัพพอร์ต (ร่างพัง เสียโควตาฟรีไปเปล่า ๆ) และเดโม
- `POST /admin/users/:id/subscription` → subscription `rove_year`, `price_thb = 0`, `provider = 'comp'`, กำหนดวันหมด
  ใช้กับครีเอเตอร์ อินฟลูฯ พาร์ตเนอร์ และทีมงาน

**ทำไมไม่เติม `ai_credits.extra`** คอมเมนต์บนคอลัมน์เขียนไว้ตรง ๆ ว่า M26 เลิกขายมันแล้ว
"ยังบวกเข้าโควตาเพื่อให้ของที่คนจ่ายไปก่อนหน้ายังใช้ได้ แต่ไม่มีใครเขียนลงมันอีกแล้ว"
([aijob.go:57](apps/api/pkg/models/aijob.go)) — มันคือหลุมศพที่ยังเปิดไฟทิ้งไว้ให้คนที่ยังอยู่ข้างใน
การเขียนแถวใหม่ลงไปคือการปลุกของที่ถูกฝังแล้ว แล้วทำให้ "เครดิตก้อนนี้ใครจ่ายค่าอะไร" ตอบไม่ได้อีก —
**เหตุผลเดียวกับที่ §B-2 ห้ามขยาย `discount_codes`**

**ทำไมไม่ทำตารางโควตาต่อผู้ใช้** มันจะเป็น **ทางปลดล็อกเส้นที่สาม** ที่ขนานกับสองเส้นที่มีอยู่ →
`unlockState` งอกกิ่งที่สาม · มิเตอร์บนจอต้องเล่าเรื่องที่สาม · และ paywall ต้องอธิบายสถานะที่ไม่มีใครซื้อ
ที่แย่กว่านั้นคือมันเป็นสิทธิ์ "ต่อคน" ในสินค้าที่หน่วยของคุณค่าคือ "ต่อทริป" (docs/decision-log.md 27 ส.ค.)

**ของแถมที่ไปโผล่ในที่ถูกต้องฟรี ๆ**

- **M28 ได้ของฟรี** — หน้าออเดอร์เห็น comp ทุกใบโดยไม่ต้องเขียนหน้าจอที่สอง และรายงานรายได้แยก
  ของแถมออกจากของที่ขายได้ด้วย `total_thb = 0` / `method = 'comp'` ไม่ต้องมีคอลัมน์ใหม่
- **การคืนเงินตอนจองไม่พัง** `refundTripPass` มีการ์ด `pass.TotalTHB <= 0` อยู่แล้ว
  ([booking.handler.go:377](apps/api/pkg/handlers/api/booking.handler.go)) — pass แถมจึงไม่มีทางกลายเป็นโค้ดคืนเงิน ฿299
  **ของที่ต้องเขียนใหม่เพื่อรองรับ comp คือศูนย์บรรทัด**
- **เพดานต้นทุนยังคุมอยู่** comp ข้ามมิเตอร์ ไม่ได้ข้าม `CheckDailyCap` — $20/วันยังเป็นเพดานเดียวกันของทั้งระบบ

**สิทธิ์ที่ใช้:** `billing.comp` (§6.1) — คนที่ comp ได้คือคนที่ออกของมูลค่าเงินได้ ไม่ใช่คนที่ดูแลผู้ใช้ได้
เพราะ ฿299 ที่แจกฟรีคือรายได้ที่หายไปเท่ากับ ฿299 ที่คืนให้ · ทุกใบลง audit พร้อมเหตุผลที่บังคับกรอก

### 6.3 D5.2 — ระงับ vs แบน (เคาะแล้ว 27 ส.ค. 2569)

**กติกาข้อเดียวที่ทำให้ทุกคำถามย่อยตอบได้:**

> **สถานะบัญชีแตะ "สิ่งที่คนนั้นทำได้ต่อจากนี้" ไม่แตะ "สิ่งที่เขาเคยทำไปแล้ว"**
> การจัดการเนื้อหาเป็นงานคนละชิ้น อยู่ที่ M29 ทำทีละชิ้น มี audit ของตัวเอง และแจ้งเจ้าของได้

ถ้าแบนแล้วซ่อนทุกอย่างอัตโนมัติ การปลดแบนต้องเปิดคืนทุกอย่าง ซึ่งแปลว่าต้องจำให้ได้ว่า
ชิ้นไหนถูกซ่อนเพราะแบน ชิ้นไหนถูกโมเดอเรเตอร์ซ่อนก่อนหน้านั้น — **ระบบสองระบบเขียนฟิลด์เดียวกัน
คือบั๊กที่รอเกิด** และมันจะเกิดตอนปลดแบน ซึ่งเป็นตอนที่มีคนกำลังโกรธอยู่แล้ว

หน้าจอแบนจึงมี checkbox **"ซ่อนเนื้อหาสาธารณะของคนนี้ด้วย"** ที่ไปเรียก action ของ M29 ทีละชิ้น
ลง audit ทีละแถว → ยกเลิกทีหลังได้แม่นยำ ไม่ใช่ผลข้างเคียงที่มองไม่เห็น

#### สามสถานะ แยกด้วย "ใครเป็นคนทำ และมันจบเองไหม"

| สถานะ | ใครตั้ง | จบยังไง |
|---|---|---|
| `deactivated` | เจ้าตัว | เจ้าตัวกลับมา login |
| `suspended` | แอดมิน | **หมดอายุเอง** ที่ `suspended_until` — ไม่ต้องมีใครจำว่าต้องกลับมาปลด |
| `banned` | แอดมิน | ไม่จบเอง ต้องมีคนกดปลด |

`suspended_until` ที่หมดอายุเองคือหัวใจของข้อนี้: การระงับ 7 วันที่ต้องพึ่งความจำของมนุษย์
คือการระงับถาวรโดยอุบัติเหตุ

#### ตารางผลกระทบ

| ของ | `suspended` | `banned` | ปลดแล้ว |
|---|---|---|---|
| เข้าใช้งาน (ทุก endpoint ที่ต้อง login) | 403 | 403 | กลับมาทันที |
| **ทริปที่เป็นเจ้าของ** | **อยู่ครบ ห้องยังทำงานต่อได้** | **อยู่ครบ** | เจ้าตัวกลับเข้าได้ |
| แพลนสาธารณะใน `/explore` + โปรไฟล์ `/u/[handle]` | หายจากหน้าสาธารณะ | หาย | **กลับมาเอง** |
| รีวิว / คอมเมนต์ / รูป | อยู่ (จัดการทีละชิ้นที่ M29) | อยู่ | — |
| แต้ม | ledger ไม่ถูกแตะ · แลกไม่ได้ | ledger ไม่ถูกแตะ · แลกไม่ได้ | แลกได้อีก |
| ยอดค้างจ่ายครีเอเตอร์ | **hold ไม่ริบ** | **hold ไม่ริบ** ต้องกด "ริบ" แยก พร้อมเหตุผล | ปล่อยจ่ายต่อ |

**ทริปไม่ถูกลงโทษ เพราะทริปเป็นของห้อง ไม่ใช่ของเจ้าของ** อีกสามคนที่กำลังจะบินเดือนหน้า
ไม่ได้ทำอะไรผิด · ถ้าจำเป็นต้องเอาเจ้าของออกจริง ๆ นั่นคือการโอนสิทธิ์เจ้าของ
ซึ่งเป็นการกระทำแยกที่มองเห็นได้ ไม่ใช่ผลพลอยได้ของปุ่มแบน

**การหายจากหน้าสาธารณะเป็น JOIN ไม่ใช่การเขียนคอลัมน์** — `ListPublic`
([trip.store.go:154](apps/api/pkg/store/trip/trip.store.go)) วันนี้กรองแค่ `visibility='public'`
ไม่ได้ดูสถานะเจ้าของเลย ต้องเพิ่มเงื่อนไข join `users.status='active'` · ทำแบบนี้แล้ว
**การปลดแบนคืนของให้เองโดยไม่ต้องมีโค้ดคืนสถานะสักบรรทัด** และไม่มีทางที่ `visibility`
ของผู้ใช้จะถูกแอดมินเขียนทับ · โปรไฟล์สาธารณะทำถูกอยู่แล้ว — `handleCreatorProfile`
เช็ก `!= UserStatusActive` มาตั้งแต่ต้น ([public.handler.go:439](apps/api/pkg/handlers/api/public.handler.go))
สถานะใหม่ทั้งสองค่าจึงมีผลกับหน้านั้นทันทีโดยไม่ต้องแก้อะไร

**แต้มไม่ถูกล้าง** ledger เป็น append-only ([points.go:22](apps/api/pkg/models/points.go)) การล้างแต้มตอนแบน
คือการทำให้คำถาม "แต้มหายไปไหน" ตอบไม่ได้ตลอดกาล · แบนคือการปิดสิทธิ์**แลก** ไม่ใช่การลบประวัติ

**ยอดค้างจ่ายไม่ถูกริบอัตโนมัติ** ค่าคอมที่เกิดจากการจองจริงคือเงินที่เกิดขึ้นแล้วในโลก —
การแบนเป็นการตัดสินใจของแพลตฟอร์ม ไม่ใช่คำพิพากษาว่าเงินก้อนนั้นไม่เคยมีอยู่ · payout
เข้าสถานะ hold แล้วต้องมีคนกด "ริบ" เป็นการกระทำแยกที่มีเหตุผลและ audit ของตัวเอง ·
**เรื่องนี้อยู่ในกองเดียวกับ D24.1 ที่รอที่ปรึกษากฎหมายอยู่** — เขียนไว้ให้เห็นว่าเป็นเรื่องกฎหมาย
ไม่ใช่เรื่อง UX

#### ที่บังคับ และราคาของมัน

บังคับใน `JwtMiddleware` ([middleware.go:69](apps/api/pkg/handlers/api/middleware.go)) ไม่ใช่ที่ login —
token อายุ 7 วัน คนที่โดนแบนวันนี้จะใช้ token ใบเดิมได้ถึงสัปดาห์หน้าถ้าเช็กแค่ตอนออก token
(เหตุผลเดียวกับ §6.1 ข้อ 2 เป๊ะ ๆ)

**ราคาคือหนึ่ง SELECT by primary key ต่อทุกรีเควสต์ที่ล็อกอิน** — ไม่ใช่แค่ฝั่งแอดมิน
ที่ปริมาณทราฟฟิกวันนี้มันคือ noise และการใส่แคชตั้งแต่วันแรกแปลว่า "แบนแล้วยังใช้ได้อีก N วินาที"
ซึ่งเป็นบั๊กเดิมในขนาดที่เล็กลง · **ใส่แคชเมื่อมันโผล่ในกราฟ latency ไม่ใช่ก่อนหน้านั้น**
และถ้าจะใส่ TTL ต้องสั้นกว่าเวลาที่ยอมให้คนที่โดนแบนยังทำอะไรได้

**403 ต้องอ่านรู้เรื่อง** หน้าที่บอกว่าถูกระงับหรือถูกแบน · เหตุผลที่แอดมินกรอก · ถ้าเป็นการระงับ
บอกวันที่กลับมาได้ · และช่องทางอุทธรณ์ — ใช้หน้าเดียวกับ 403 ของสิทธิ์ไม่พอใน §6.1

### 6.4 D5.3 — ข่าว/บทความอยู่ในตาราง (เคาะแล้ว 27 ส.ค. 2569)

**คำตอบ: ตาราง `articles` · body เก็บเป็น Markdown · ไม่ทำ WYSIWYG**

#### ข้อแรกตัดจบไปแล้วตั้งแต่ §6.1

เหตุผลทั้งหมดที่ทำสิทธิ์แบบเลือกได้รายคนคือ **"เพิ่มคนดูแลข่าวคนหนึ่ง"** — คนที่ไม่ใช่ dev
ถ้าบทความอยู่เป็นไฟล์ MDX ในรีโป สิทธิ์ `articles.publish` จะไม่มีความหมายอะไรเลย เพราะของจริงที่คนนั้นต้องมีคือ
**สิทธิ์ push เข้ารีโปกับสิทธิ์ตัด release** ซึ่งมากกว่าสิทธิ์แอดมินทุกใบรวมกัน
เลือก MDX = ยกเลิก §6.1 ครึ่งหนึ่งโดยปริยาย

#### ข้อสองคือรูปร่างของ pipeline ที่มีอยู่จริง

`release.yml` ยิงจาก **tag `v*` เท่านั้น** ([.github/workflows/release.yml:3](.github/workflows/release.yml))
"แก้ข่าว = deploy หนึ่งครั้ง" จึงไม่ใช่ราคาที่แท้จริง ราคาจริงคือ

> **แก้คำผิดในข่าวหนึ่งคำ = ตัด release หนึ่งตัว = ส่งทุก commit บน main ที่ยังไม่ปล่อยขึ้น production ไปด้วย**

จังหวะของเนื้อหา (วันละหลายครั้ง แก้คำผิดทันทีที่เห็น) กับจังหวะของโค้ด (ปล่อยเมื่อพร้อม)
ไม่ใช่จังหวะเดียวกัน และการมัดสองอย่างนี้เข้าด้วยกันทำให้ **ทั้งสองฝั่งช้าลง** —
คนเขียนข่าวรอ release ส่วนคนเขียนโค้ดถูกกดดันให้ปล่อยเพราะมีคำผิดค้างอยู่

#### ข้อสาม: "ต้องทำ SEO เอง" ไม่ใช่ข้อเสียของฝั่งตาราง

ตอนเขียน §B-1 ใส่ข้อนี้ไว้ในช่องเสียของตาราง ซึ่งไม่ยุติธรรม — วันนี้ทั้งแอปไม่มี `app/sitemap.ts`
ไม่มี `robots.ts` และมี `generateMetadata` อยู่ไฟล์เดียวคือ `app/u/[handle]` · **MDX ไม่ได้แถม
sitemap หรือ metadata มาให้** งานชิ้นนี้เท่ากันทั้งสองทาง มันจึงหักล้างกันในการเปรียบเทียบ

#### สิ่งที่ตัดออกเพื่อให้ราคาสมเหตุสมผล

**ไม่ทำ rich-text WYSIWYG** — กล่อง Markdown + ปุ่ม preview ที่เรนเดอร์ด้วยตัวเรนเดอร์เดียวกับหน้าจริง

| ทำไม | |
|---|---|
| **ความปลอดภัย** | WYSIWYG คายเป็น HTML ซึ่งแปลว่ามี sanitizer หนึ่งตัวที่ต้องดูแลตลอดไปบนหน้าสาธารณะ · Markdown ที่ปิด raw HTML ไม่มีพื้นผิวนั้น |
| **ขนาด** | ไม่ต้องเพิ่ม editor lib เข้า `package.json` ที่วันนี้ยังไม่มีสักตัว |
| **ทางถอย** | body เป็น Markdown แปลว่าถ้าวันหนึ่งอยากย้ายไปเป็นไฟล์จริง ๆ มันคือ `SELECT` แล้วเขียนลงดิสก์ ไม่ใช่การแปลงฟอร์แมต |

**อัปโหลดรูปไม่ใช่ของใหม่** — `s.storage.Put` + แพตเทิร์นใน [photo.handler.go:106](apps/api/pkg/handlers/api/photo.handler.go)
มีครบแล้ว (R2 จริง, ดิสก์ในเครื่องตอน dev) งานคือคัดลอกราวยี่สิบบรรทัดกับเพิ่มบัคเก็ต ไม่ใช่การต่อ storage

**ตั้งเวลาเผยแพร่ไม่ต้องมี cron** — หน้าสาธารณะกรอง `status='published' AND published_at <= NOW()`
ไม่มี job ไหนต้องวิ่งมาพลิกธง · งานที่ไม่มีอยู่คืองานที่ไม่พัง

#### รูปร่างตาราง (ขั้นต่ำที่ธุรกิจต้องมี ไม่มากกว่านั้น)

```
articles (
  id, slug, locale, status, title, excerpt, body_md, cover_url,
  category, author_id, poi_id NULL, destination_country NULL,
  seo_title, seo_description, published_at, created_at, updated_at
)
-- unique (locale, slug)
```

- **`locale` ต้องมีตั้งแต่แถวแรก** ทั้งที่วันนี้มีแต่ภาษาไทย — [docs/i18n-plan.md](docs/i18n-plan.md) เขียนไว้แล้วว่า
  สองภาษาจะมา การเติมคอลัมน์นี้ทีหลังแปลว่าต้องแก้ unique index, backfill slug และแก้ route สาธารณะพร้อมกัน
  ตอนที่มีบทความจริงอยู่ข้างในแล้ว · **หนึ่งคอลัมน์วันนี้ ถูกกว่า migration ที่มีคนอ่านอยู่**
- **`poi_id` / `destination_country` คือเหตุผลที่บทความอยู่บน ROVE ไม่ใช่บน Medium** (§B-1 พูดข้อนี้ไว้แล้ว)
  บทความต้องลิงก์เข้า `/explore` ได้ และหน้าปลายทางต้องลิงก์กลับมาที่บทความได้ ·
  **ถ้าลิงก์สองทางนี้ไม่ได้ทำ ให้ไปเขียนบน Medium หรือเพจแล้วตัด CMS ทิ้งจาก M29 เลย** —
  นั่นคือคำตอบที่ซื่อสัตย์ และมันถูกกว่าการมี CMS ที่ไม่มีใครใช้

#### ที่พ่วงมา

- `articles.write` / `articles.publish` ที่แยกกันไว้ใน §6.1 มีความหมายจริงตอนนี้: เขียนได้แต่ปล่อยไม่ได้ = ร่างอย่างเดียว
- ทุกครั้งที่กดเผยแพร่ ลง `admin_audit_logs` เหมือน mutation อื่น — ของที่ออกไปข้างนอกแล้วต้องตอบได้ว่าใครปล่อย
- หน้าสาธารณะต้อง revalidate ตอนเผยแพร่ ไม่งั้นข่าวที่ปล่อยแล้วยังไม่ขึ้นเพราะแคชหน้าเดิมค้างอยู่

### 6.5 D5.4 — เลื่อน M30 อย่างมีเงื่อนไข (เคาะแล้ว 27 ส.ค. 2569)

**คำตอบ: ยังไม่สร้าง `campaigns` · M30 ลงไปอยู่ท้ายแถวหลัง M28/M29 · ใช้ของที่มีอยู่ไปก่อน**

#### เหตุผลที่หนักที่สุดคือคำตอบว่า "ยังไม่รู้"

ตอนถามว่าคูปองที่คิดไว้ลดเป็นบาทหรือเป็นเปอร์เซ็นต์ คำตอบคือยังไม่รู้ — และนั่นไม่ใช่ช่องว่างของข้อมูล
มันคือคำตอบของ D5.4 เอง: **การออกแบบตารางส่วนลดโดยไม่รู้ว่าจะลดเป็นอะไร คือการเดารูปร่างของตาราง**
แล้วสิ่งที่เดาไว้จะกลายเป็นข้อจำกัดตอนที่แคมเปญจริงมาถึง ซึ่งเป็นวิธีที่ `discount_codes`
กลายเป็นตารางที่ขยายไม่ได้มาแล้วหนึ่งรอบ (§B-2)

#### ของที่มีอยู่ทำได้แค่ไหน

| ต้องการ | วันนี้ทำได้ไหม |
|---|---|
| ให้ส่วนลดคนใดคนหนึ่ง (อินฟลูฯ, ซัพพอร์ต, เพื่อน) | ✅ `POST /admin/discount-codes` — ผูก `@handle`, สูงสุด ฿299, อายุ 90 วัน |

**คูปอง 100% กับ comp ฿0 ทับกัน — เลือกใช้ตามนี้:** comp คือการ*ปลดล็อกให้เลย* ใช้เมื่อรู้ตัวคน/ทริปแน่นอน
(ซัพพอร์ต, เดโม, ทีมงาน) · โค้ดส่วนลดคือของที่*ต้องมีคนไปกรอก* ใช้เมื่ออยากให้มีการกด อยากวัด conversion
หรืออยากให้คนรู้สึกว่าถือของมีค่าอยู่ในมือ — สองอย่างนี้ไม่ได้ซ้ำซ้อน มันตอบคนละคำถาม

#### สิ่งที่ทำแทนใน M27 (ครึ่งวัน ไม่ใช่หนึ่งสัปดาห์)

เครื่องมือที่ต้องยิงด้วย `curl` คือเครื่องมือที่ไม่มีใครใช้ → หน้าจอบาง ๆ ให้ endpoint ที่เขียนเสร็จแล้ว:
ฟอร์มออกโค้ด (handle + จำนวนเงิน + จำนวนวัน) และตารางโค้ดที่ออกไปแล้ว — ใครถือ ใช้ไปหรือยัง หมดอายุเมื่อไหร่
นี่คือแพตเทิร์นเดียวกับ §1 "เปิดประตูให้ของที่เขียนเสร็จแล้ว" ไม่ใช่ฟีเจอร์ใหม่

#### เงื่อนไขที่บอกว่าถึงเวลาทำ M30 — เขียนไว้เพื่อไม่ให้เลื่อนแบบลอย ๆ

ข้อใดข้อหนึ่งพอ:

1. **มีแคมเปญจริงที่ต้องใช้โค้ดเดียวหลายคนใช้** — โค้ดในโพสต์, โค้ดของอินฟลูฯ, โค้ดในงานอีเวนต์
2. **การออกโค้ดรายคนเริ่มกินเวลา** — เกินราว 20 ใบต่อเดือนแปลว่ากำลังทำงานของเครื่องด้วยมือ
3. **ตอบได้แล้วว่าลดเป็นบาทหรือ %** และตอบจากแคมเปญจริง ไม่ใช่จากการวางแผนเผื่อ

**เมื่อถึงวันนั้น กติกาเดิมยังอยู่:** ตาราง `campaigns` + `campaign_redemptions` แยกใหม่ **อย่าขยาย `discount_codes`** (§B-2)

### 6.6 D5.5 — เรตอยู่ในโค้ด · DB เก็บ "ตัวตน" ของพาร์ตเนอร์ (เคาะแล้ว 27 ส.ค. 2569)

**คำตอบ: ตอบข้อ (ข) แต่ขยับเป้า** — ไม่ย้ายเรตเข้า DB · หน้าจอเรตเป็น read-only ·
**แต่สร้างตาราง `partners` ที่เก็บตัวตน ไม่เก็บเรต**

#### ทำไมไม่ย้ายเรต: ยังไม่มีสัญญาจริงสักเจ้า

เรตใน `partnerCommissionRate` ([revenue.go:87](apps/api/pkg/domain/revenue.go)) วันนี้คือค่าประมาณจากหน้าเว็บ affiliate
ไม่ใช่ตัวเลขที่ตกลงกับใคร · **ตาราง config ที่เก็บตัวเลขซึ่งยังไม่มีใครสัญญาไว้ ทำให้ค่าประมาณดูเหมือนข้อเท็จจริง**
`const` ที่มีคอมเมนต์กำกับว่ามาจากไหนซื่อสัตย์กว่าแถวในตารางที่มีช่อง "แก้ไข" อยู่ข้าง ๆ

และมันเปลี่ยนคำถามด้วย: การย้ายเข้า DB มีค่าตอนที่ "แก้เรตแล้วต้องมีผลทันทีโดยไม่ deploy"
ซึ่งเกิดขึ้นตอนมีสัญญาที่ระบุวันมีผลบังคับ — วันนี้ยังไม่มีวันนั้นให้เคารพ

#### แต่ §B-3 พูดถูก และมีหลักฐานชิ้นใหม่

ที่ขาดจริงไม่ใช่หน้าจอแก้ตัวเลข แต่คือ **ตัวตนของพาร์ตเนอร์** — และวันนี้มันพังอยู่จริง ๆ:

> `rabbitcare` ถูกอ้างเป็นพาร์ตเนอร์ของ offer ประกัน ([affiliate.go:154](apps/api/pkg/services/affiliate/affiliate.go))
> แต่ **ไม่มีอยู่ใน `partners` slice** ([affiliate.go:57](apps/api/pkg/services/affiliate/affiliate.go)) →
> `BuildLink` ตกไป `fallbackURL` **เงียบ ๆ** ไม่มีใครรู้ว่าคลิกนั้นไม่มีทางกลายเป็นค่าคอม

ตาราง `partners` จึงเก็บ: `key`, ชื่อ, เปิด/ปิด, ประเภทที่รองรับ, ผู้ติดต่อ,
**สถานะสัญญา** (ยังไม่คุย / กำลังคุย / เซ็นแล้ว) และ postback ล่าสุดเมื่อไหร่ ·
พร้อมเทสต์ที่ยืนยันว่าทุก partner ที่ถูกอ้างใน offers มีแถวอยู่จริง — **บั๊กชนิดที่ทำให้รายได้หายจะได้ดัง ไม่ใช่เงียบ**

#### กติกาความจริงหนึ่งเดียว

> **โค้ดเป็นเจ้าของ "เรต" · DB เป็นเจ้าของ "ตัวตน"**

ตัวตนเปลี่ยนบ่อย (เปิด/ปิดเจ้าไหน ติดต่อใคร คุยถึงไหนแล้ว) เรตแทบไม่เปลี่ยน — แยกตามอัตราการเปลี่ยน
ไม่ใช่ตามว่ามันอยู่ใกล้กันในหัว · หน้าจอพาร์ตเนอร์ต้องเขียนไว้บนจอตรง ๆ ว่า
**"เรตมาจากโค้ด แก้ได้ด้วยการ deploy เท่านั้น"** พร้อมป้ายว่าตัวเลขนี้เป็นค่าประมาณเพราะยังไม่มีสัญญา —
หน้าจอ read-only ที่ไม่บอกว่าทำไมแก้ไม่ได้ คือหน้าจอที่จะมีคนมาถามทุกเดือน

#### วันที่ต้องย้ายเรตเข้า DB

**สัญญาฉบับแรกที่มีวันมีผลบังคับและเรตต่างจากค่าประมาณ** ตอนนั้น `commission_rates` (มี `effective_from`)
เป็นงานเล็ก เพราะ `partners` มีอยู่แล้วและ `share_percent` ถูก snapshot ลงแถวตอนสร้างอยู่แล้ว
([partner.go:74](apps/api/pkg/models/partner.go)) — **แถวเก่าปลอดภัยตั้งแต่วันนี้ ไม่ต้องรอตาราง config มาช่วย**
