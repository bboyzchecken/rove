## 2. กอง A — สิ่งที่ "แอดมินต้องจัดการได้อยู่แล้ว"

คือข้อ 1 ของโจทย์: จัดการผู้ใช้ / ชาวโรฟ · ระงับ · แบน · ให้สิทธิ์ AI
แยกตามว่า **ต้องแตะอะไรถึงจะได้มา**

### A-1 · ต่อสายอย่างเดียว (backend เสร็จแล้ว 100%)

| งาน | endpoint ที่มีอยู่ | ต้องทำ |
|---|---|---|
| แก้/เพิ่ม POI | `POST/PATCH /admin/poi` | ฟอร์ม + ตารางที่แก้ได้ |
| จัดการตัวละคร | `GET/POST /admin/characters` | หน้ารายการ + ฟอร์ม |
| คิว lead ของเอเจนต์ | `GET /admin/leads`, `PATCH /admin/leads/:id` | ตาราง + เปลี่ยนสถานะ (`new→sent→contacted→won/lost`) + ช่อง `admin_note` |
| รายงานจ่ายครีเอเตอร์ | `GET/POST /admin/payouts` | รายงานรายเดือน + ปุ่มปิดยอดทีละคน (ขั้นต่ำ ฿300 ตาม `domain.MinimumPayoutTHB`) |

**นี่คือกองที่คุ้มที่สุดต่อวันทำงาน** — ไม่มี migration ไม่มี endpoint ใหม่ ไม่มีการตัดสินใจทางธุรกิจ

### A-2 · เขียน endpoint ใหม่ แต่ data model รองรับอยู่แล้ว

| งาน | ของที่มีรองรับอยู่ | ที่ขาด |
|---|---|---|
| ลิสต์/ค้นหาผู้ใช้ | ตาราง `users` ครบ | `UserStore.List(filter, cursor)` + `GET /admin/users` |
| หน้าโปรไฟล์ผู้ใช้รายคน (มุมแอดมิน) | ทริป, `user_points`, `orders`, `creator_earnings`, `ai_jobs` มีครบทุกตาราง | endpoint รวมร่างเดียว `GET /admin/users/:id` |
| ปรับแต้มมือ | `PointsReasonAdjustment` **นิยามไว้แล้วแต่ไม่มีใครเรียก** ([points.go:17](apps/api/pkg/models/points.go)) | `POST /admin/users/:id/points` + บังคับให้กรอกเหตุผล |
| เปลี่ยน role | `users.role` | `PATCH /admin/users/:id/role` + กันแอดมินคนสุดท้ายลดสิทธิ์ตัวเอง (`CountAdmins` มีอยู่แล้ว) |
| ดู/retry AI job ที่ค้าง | `ai_jobs` มี `status='failed'` + `error` | `GET /admin/ai/jobs` + ปุ่ม retry |

### A-3 · ต้องแก้ schema หรือบังคับกฎเพิ่ม

| งาน | ทำไมยังไม่ได้ | ที่ต้องทำ |
|---|---|---|
| **ระงับ / แบน** | `status` ไม่ถูกบังคับที่ไหนเลย (§1.1) | (1) เพิ่มค่า `suspended` / `banned` + คอลัมน์ `suspended_until`, `status_reason`, `status_by` (2) **บังคับใน `JwtMiddleware`** ไม่ใช่แค่ตอน login — ไม่งั้น token ที่ออกไปแล้วยังใช้ได้จนหมดอายุ (3) ตัดสินว่าทริปที่เขาเป็นเจ้าของและแพลนสาธารณะของเขาจะเป็นยังไง → **D5.2** |
| **ให้สิทธิ์ AI** | `ai_credits` เป็น **per-trip** (`trip_id` เป็น primary key) ไม่มีที่เก็บสิทธิ์ระดับ "คน" ([aijob.go:57](apps/api/pkg/models/aijob.go)) | สองทางเลือกใน **D5.1** — เติม `extra` ให้ทริปใดทริปหนึ่ง (ทำได้พรุ่งนี้) vs ตารางโควตาต่อผู้ใช้ (ตารางใหม่ + แก้จุดตรวจโควตา) |
| **audit log ของแอดมิน** | `activity_logs` ผูก `trip_id` เสมอ ([collab.go:50](apps/api/pkg/models/collab.go)) — บันทึกการกระทำนอกทริปไม่ได้ | ตาราง `admin_audit_logs` (actor, action, target_type, target_id, before/after JSON, ip, at) — **ต้องขึ้นพร้อมปุ่มแบนปุ่มแรก ไม่ใช่ตามหลัง** |

## 3. กอง B — สิ่งที่ธุรกิจต้องมี แต่ยังไม่เคยวางแผนไว้

คือข้อ 2 ของโจทย์ ทั้งหมดนี้ **ไม่มีตาราง ไม่มี endpoint ไม่มีหน้าจอ** เว้นแต่ระบุไว้เป็นอย่างอื่น

### B-1 · ข่าว / บทความ (CMS) — เริ่มจากศูนย์

ไม่มี model ชื่อไหนใกล้เคียงเลยใน `pkg/models/` และไม่มี route `/blog` หรือ `/news` ใน `apps/web/app`

ต้องตัดสิน **D5.3** ก่อน: เขียนตาราง `articles` เอง (แก้ในเว็บได้ ไม่ต้อง deploy · แต่ต้องทำ editor, อัปโหลดรูป, ร่าง/เผยแพร่, SEO เอง) หรือวางไฟล์ MDX ในรีโป (ไม่ต้องเขียนหลังบ้านเลย · แต่แก้ข่าวหนึ่งชิ้น = deploy หนึ่งครั้ง และคนที่ไม่ใช่ dev แก้ไม่ได้)

ถ้าเลือกตาราง ขั้นต่ำที่ธุรกิจต้องมี: หมวดหมู่, ปก, สถานะ (draft/scheduled/published), เวลาเผยแพร่, ผู้เขียน, slug, SEO title/description, และ **ผูกกับ POI/ปลายทางได้** — เพราะเหตุผลเดียวที่บทความควรอยู่บนนี้แทนที่จะเป็น Medium คือมันต้องลิงก์กลับเข้า explore ได้

### B-2 · คูปอง / แคมเปญ — **ไม่ใช่การขยายตารางเดิม**

มีตาราง `discount_codes` อยู่แล้ว แต่มันคือ "แต้มแลกโค้ด" ของผู้ใช้ (A12.10) ไม่ใช่คูปองการตลาด:

| `discount_codes` วันนี้ | คูปองการตลาดต้องการ |
|---|---|
| `user_id` **not null** — โค้ดเป็นของคนเดียว | โค้ดเดียวคนใช้ได้หลายคน |
| `points_spent` not null — โค้ดที่มีอยู่คือโค้ดที่จ่ายแต้มแล้ว | ไม่มีแต้มมาเกี่ยวเลย |
| จำนวนเงินตายตัว ฿50/฿100/฿300 (`RedemptionTiers`) | ลด % ก็ได้, มีเพดาน, มียอดขั้นต่ำ |
| ใช้ครั้งเดียว | โควตารวม + โควตาต่อคน |
| อายุ 180 วันตายตัว | มีวันเริ่ม–วันจบ |
| ไม่มีสถานะ | เปิด/ปิด/หยุดชั่วคราว |

→ **เสนอ:** ตาราง `campaigns` + `campaign_redemptions` แยกใหม่ แล้วให้จุดคิดเงินรับได้ทั้งสองชนิด · **อย่าขยาย `discount_codes`** — ตารางนั้นถือหนี้สินที่ผู้ใช้จ่ายแต้มซื้อไปแล้ว การเติมคอลัมน์ nullable ห้าตัวเข้าไปทำให้ "โค้ดใบนี้ใครจ่ายค่าอะไร" ตอบไม่ได้อีกต่อไป

ก่อนทำต้องตอบ **D5.4**: วันนี้ ROVE เก็บเงินอย่างเดียวคือ **เครดิต AI** (`DiscountScopeAICredits`) — คูปองจะเอาไปลดอะไร ถ้ายังไม่มีของอื่นให้ขาย

### B-3 · ค่าคอมมิชชั่น — ของมีครบ แต่แก้ได้ด้วยการ deploy เท่านั้น

| ตัวเลข | อยู่ที่ไหน | แก้ยังไงวันนี้ |
|---|---|---|
| เรตค่าคอมต่อพาร์ตเนอร์ (agoda 5%, booking 4%, …) | `partnerCommissionRate` map ใน [revenue.go:87](apps/api/pkg/domain/revenue.go) | แก้โค้ด + deploy |
| ส่วนแบ่งครีเอเตอร์ 30% | `CreatorSharePercent` | แก้โค้ด + deploy |
| ขั้นต่ำจ่าย ฿300 | `MinimumPayoutTHB` | แก้โค้ด + deploy |
| อัตราแลกแต้ม 8 แต้ม = ฿1 | `PointsPerBahtRedeemed` | แก้โค้ด + deploy |
| รายชื่อพาร์ตเนอร์ + catalogue ของข้อเสนอ | slice ใน [affiliate.go](apps/api/pkg/services/affiliate/affiliate.go) | แก้โค้ด + deploy |

**ที่ขาดจริง ๆ ไม่ใช่ "หน้าจอแก้ตัวเลข" แต่คือ "ตัวตนของพาร์ตเนอร์ในระบบ"** — วันนี้พาร์ตเนอร์เป็นแค่ string ในคอลัมน์ `creator_earnings.partner` ไม่มีตารางที่บอกว่ารายนี้เปิด/ปิดอยู่, เรตเท่าไหร่, ตั้งแต่เมื่อไหร่, ติดต่อใคร, postback เข้ามาล่าสุดเมื่อไหร่

ข้อที่ต้องเขียนลง spec ให้ชัด: **เรตต้องมีผลไปข้างหน้าเท่านั้น** เปลี่ยนเรตแล้ว `creator_earnings` แถวเก่าต้องไม่ขยับ ไม่งั้นยอดที่จ่ายไปแล้วกับรายงานจะไม่ตรงกัน → โชคดีที่ `share_percent` ถูกเก็บลงแถวตอนสร้างอยู่แล้ว ([partner.go:74](apps/api/pkg/models/partner.go)) ตาราง config ใหม่แค่ต้องมี `effective_from`

### B-4 · โมเดอเรชัน — ช่องว่างที่ใหญ่ที่สุดและถูกมองข้ามที่สุด

`grep -i "report|abuse|moderat"` ทั้ง `apps/api/pkg` = **ไม่เจออะไรเลย**

ของที่ผู้ใช้เผยแพร่สู่สาธารณะได้วันนี้: แพลนสาธารณะ (`trips.visibility='public'`), รีวิว (`trip_reviews`), รูป (`trip_photos`), คอมเมนต์ (`comments`), โปรไฟล์ `/u/[handle]` (ชื่อ, handle, รูป)

ธุรกิจต้องมีอย่างน้อย: ปุ่มรายงานฝั่งผู้ใช้ → คิวรายงานฝั่งแอดมิน → ซ่อน/ลบเนื้อหา → บันทึกลง audit log → แจ้งเจ้าของ

ถ้ามีข่าว บทความ และคูปอง แต่ลบรีวิวหยาบคายออกจากหน้าสาธารณะไม่ได้ นั่นคือลำดับความสำคัญที่กลับหัว

### B-5 · เงิน ใบเสร็จ และการคืนเงิน

`orders` / `subscriptions` มีครบ ([billing.go](apps/api/pkg/models/billing.go)) แต่ **แอดมินไม่มีทางเห็นแม้แต่ใบเดียว** — `registerBillingRoutes` แขวนอยู่ใต้ `users/me` เท่านั้น

- `Order.Status` มีค่า refunded และมี `RefundedAt` เตรียมไว้ แต่ **ไม่มี code path ไหนเซ็ตมัน**
- คอมเมนต์ในโมเดลบอกชัดว่า order เขียนแล้วห้ามแก้: การคืนเงินคือการเปลี่ยนสถานะ และการแก้คือออกใบใหม่ — spec ของหน้าคืนเงินต้องเคารพข้อนี้
- `Order.Simulated` แปลว่ายังไม่มี gateway จริง → หน้าคืนเงินวันนี้คือ "ทำเครื่องหมายว่าคืนแล้ว" ไม่ใช่ "โอนเงินคืน" และต้องเขียนบนจอให้ตรงตามนั้น

### B-6 · จ่ายเงินครีเอเตอร์จริง

`payouts` บันทึก "ใคร งวดไหน เท่าไหร่ สถานะอะไร" แต่ **ไม่มีที่เก็บว่าจะโอนเข้าบัญชีไหน** — ไม่มีชื่อธนาคาร ไม่มีเลขบัญชี ไม่มีข้อมูลภาษี ไม่มี KYC

→ วันนี้ปิดยอดในระบบได้ แต่การโอนจริงต้องไปถามกันนอกระบบ · ถ้าจะมีครีเอเตอร์จริง อันนี้ต้องมาพร้อม **D5.6** (เก็บข้อมูลอ่อนไหวแค่ไหน ใครเห็นได้บ้าง เก็บนานแค่ไหน)

### B-7 · ของ ops ที่เหลือ

| เรื่อง | สภาพวันนี้ |
|---|---|
| Feature flags | hardcode ใน [lib/flags.ts](apps/web/lib/flags.ts) ฝั่ง web — เปิด/ปิดฟีเจอร์ = deploy |
| ประกาศถึงผู้ใช้ | `notifications` ยิงได้ทีละคนจาก event ในทริปเท่านั้น ([community.handler.go](apps/api/pkg/handlers/api/community.handler.go)) ไม่มี broadcast |

## 4. Layout และธีมของแอดมิน

### 4.1 กฎที่ห้ามแหก

[styles/brand.css](apps/web/styles/brand.css) เขียนไว้ว่าเป็น **ที่เดียว** ที่มีสีของแบรนด์ และบรรทัดสุดท้ายของไฟล์บอกว่า dark theme คือ "การออกแบบใหม่ ไม่ใช่การสลับ token"

→ ธีมแอดมินจึงต้องเป็น **scope ที่เพิ่มในไฟล์เดิม** ไม่ใช่ไฟล์สีที่สอง:

```css
/* ต่อท้าย :root ใน brand.css */
[data-surface='admin'] { --brand-bg: 17 26% 11%; --brand-surface: 17 20% 16%; ... }
```

แล้วใส่ `data-surface="admin"` เฉพาะใต้ layout ของแอดมิน — Tailwind mapping ใน `globals.css` **ไม่ต้องแก้แม้แต่บรรทัดเดียว** เพราะทุก utility อ่าน `hsl(var(--brand-*))` อยู่แล้ว

### 4.2 สีที่เสนอ (สีเดิม เข้มขึ้น ไม่ใช่ชุดใหม่)

| token | ฝั่งผู้ใช้ | ฝั่งแอดมิน (เสนอ) | เหตุผล |
|---|---|---|---|
| `--brand-bg` | ขาว | espresso เข้ม `17 26% 11%` | espresso คือสีตัวอักษรของแบรนด์อยู่แล้ว → กลับด้านมาเป็นพื้น ได้ธีมเข้มที่ยังเป็นสีเดียวกับแบรนด์ ไม่ใช่เทากลาง ๆ ของ dashboard ทั่วไป |
| `--brand-surface` | `30 10% 96%` | `17 20% 16%` | การ์ดลอยจากพื้นด้วยความสว่าง ไม่ใช่ด้วยเงา (คงหลักการ flat เดิม) |
| `--brand-espresso` (ตัวอักษร) | `17 26% 19%` | ครีม `30 20% 92%` | |
| `--brand-muted` | `22 18% 43%` | `24 12% 62%` | ต้องผ่าน 4.5:1 บนพื้นใหม่ |
| `--brand-primary` | terracotta `15 65% 58%` | **คงเดิม** | ปุ่มหลักและ active state เท่านั้น — บนพื้นเข้มมันเด่นกว่าเดิมด้วยซ้ำ |
| accent 4 สี | บล็อกสีสนุก ๆ | ลดความอิ่ม ใช้เป็น **สถานะ** เท่านั้น: matcha = สำเร็จ · sun = รอ/เตือน · joyfull = ข้อมูล · danger = อันตราย | **นี่คือจุดที่ "เลิกการ์ตูน" เกิดขึ้นจริง** — ไม่ใช่ที่การเปลี่ยนสี แต่ที่การเลิกใช้สีเพื่อความสนุก |
| `--brand-radius` | 24px | 10px (`-sm` 6px) | ตารางข้อมูลที่มุมโค้ง 24px อ่านยาก |
| เงา | แทบไม่ใช้ | คงหลักเดิม แต่บนพื้นเข้มต้องเป็น `rgba(0,0,0,…)` ไม่ใช่สี espresso | |
| ฟอนต์ | Inter + Noto Sans Thai | **คงเดิม** และให้ `.nums` (tabular) เป็นค่าเริ่มต้นในตารางทุกใบ | |

### 4.3 โครงหน้าจอ

- **sidebar ซ้ายถาวร** (ยุบได้) + topbar บาง ๆ (ค้นหาข้ามระบบ, ป้ายบอก env/stub, บัญชีแอดมิน) + content เต็มความกว้าง
- **desktop-first** — เป็น **ข้อยกเว้นที่ตั้งใจ** ของ `DEV_SPEC` §7 ที่กำหนด mobile-first ทั้งโปรเจกต์ ต้องเขียนเหตุผลลง spec: งานแอดมินคือตารางกับฟอร์ม ไม่ใช่การยืนดูบนรถไฟ · มือถือรองรับแค่ "อ่านตัวเลข + ตอบ lead"
- **primitives ใหม่อยู่ใน `components/admin/ui/`** ห้ามยัดเข้า `components/ui/` ซึ่งเป็นของฝั่งผู้ใช้: `DataTable` (sort / paginate / เลือกหลายแถว), `FilterBar`, `Drawer` รายละเอียด, `ConfirmDangerDialog` (พิมพ์ยืนยันสำหรับแบน/ลบ), `StatusPill`, `KeyValueList`, `AuditTrail`, `MoneyCell`
- ทุกหน้าที่ทำอะไรถาวรได้ ต้องมีสามอย่างเสมอ: **ช่องเหตุผลที่บังคับกรอก · แถบ audit ของ target นั้น · ทางถอย** (ถ้าถอยไม่ได้ ต้องบอกก่อนกด ไม่ใช่หลังกด)

### 4.4 Routing — มีกับดักหนึ่งอัน

วันนี้ `app/(app)/admin/page.tsx` → `/admin` (อยู่ใน `AppShell` ของผู้ใช้) และ `app/admin/login/page.tsx` → `/admin/login`

**ถ้าสร้าง `app/admin/page.tsx` โดยไม่ลบของเดิมก่อน = build error** (สอง route group ให้ path เดียวกัน)

เสนอ: ย้ายทั้งก้อนไป `app/(admin)/admin/**` พร้อม `layout.tsx` ของตัวเอง แล้ว **ลบ `app/(app)/admin` ทิ้ง** · `app/admin/login` อยู่ที่เดิม (คนละ layout กับ dashboard — หน้า login ไม่ควรมี sidebar)

[proxy.ts](apps/web/proxy.ts) ไม่ต้องแก้เลย: `/admin` อยู่ใน `GUARDED` และ `/admin/login` อยู่ใน `OPEN` แล้ว — ตราบใดที่ URL ไม่เปลี่ยน

### 4.5 สองข้อที่คนมักลืมแล้วบานปลาย

1. **mock/live ต้องเดินได้ทั้งคู่** — repo pattern บังคับให้ทุกหน้าจอใหม่มีทั้ง [live/repo.ts](apps/web/lib/data/live/repo.ts) และ [mock/repo.ts](apps/web/lib/data/mock/repo.ts) · นี่คือ **ประมาณครึ่งหนึ่งของงานฝั่ง UI** ไม่ใช่ของแถม
2. **ภาษา** — [docs/i18n-plan.md](docs/i18n-plan.md) เขียนไว้ตั้งแต่บรรทัดแรกว่าขอบเขต i18n **ไม่รวมหน้า admin** → Phase 5 เป็นไทยล้วนโดยตั้งใจ และต้องเขียนไว้ในหัว spec ไม่งั้นรอบหน้าจะมีคนมาไล่ถอดคีย์
